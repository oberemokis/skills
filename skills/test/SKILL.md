# Test

> Точка входа: [skills/core](../core/SKILL.md). Если core ещё не прочитан, прочитать его до этого скилла.

Здесь собраны методологии и правила, общие для всех тестов. Как писать тесты на конкретном инструменте, смотри в `stack`: этот скилл не знает про раннеры и их API. В примерах `test`, `expect`, `render`, `http` условные имена, подставляй те, что в проекте.

## Что проверяет тест

Проверяй наблюдаемое поведение через публичный интерфейс. Наблюдаемое это то, что видит пользователь модуля: возвращённое значение, отрендеренный текст, отправленный запрос, записанная строка, выброшенная ошибка. Не наблюдаемое: вызванный внутренний метод, значение приватного поля, порядок внутренних шагов, количество перерисовок.

Критерий один. Тест переживает переписывание внутренностей модуля без единой правки в самом тесте. Не переживает, значит проверяет реализацию, и его придётся править при каждом рефакторинге, пока он не начнёт врать.

## Граница подмены

Подменяй то, что выходит за пределы процесса. Всё внутри процесса оставляй реальным.

| Что подменяется | Почему |
| --- | --- |
| сеть | недоступна в тесте, медленная, принадлежит не нам |
| время, таймеры, задержки | тест не должен ждать и не должен зависеть от даты запуска |
| случайность и генераторы идентификаторов | результат обязан быть одним и тем же при каждом прогоне |
| файловая система, дочерние процессы | оставляют следы, которые протекают в следующий тест |
| переменные окружения | поведение теста не должно зависеть от машины |

Не подменяй ничего своего: модули, сторы, композаблы, роутер, валидацию, форматирование, вычисления, слои зависимостей. Подменив свой код, ты перестаёшь замечать, что он сломан.

Это правило важнее деления на формы тестов. Если для теста приходится подменять свой модуль, проблема не в тесте, а в том, что логика слиплась с вводом-выводом.

### Проектирование под подмену

Граница процесса подменяется легко или тяжело в зависимости от того, как написан код, который её касается. Два приёма делают её лёгкой.

Передавай внешнюю зависимость аргументом, а не создавай внутри. Функция, которая сама конструирует клиента по переменным окружения, не подменяется вообще, и тест приходится вести через мок модуля.

```ts
// хорошо: клиент приходит извне
function processPayment(order, paymentClient) {
  return paymentClient.charge(order.total)
}
```

```ts
// плохо: клиент создаётся внутри, подменить его нечем
function processPayment(order) {
  const paymentClient = new PaymentClient(process.env.PAYMENT_KEY)

  return paymentClient.charge(order.total)
}
```

Описывай границу как набор конкретных операций, а не как один универсальный запрос. Тогда подмена возвращает одну форму на операцию, и в тестовой подготовке не появляется условная логика, разбирающая, какой именно запрос пришёл.

```ts
// хорошо: каждая операция подменяется отдельно
const api = {
  getUser: (userId) => request(`/users/${userId}`),
  getOrders: (userId) => request(`/users/${userId}/orders`),
}
```

```ts
// плохо: подмена вынуждена ветвиться по адресу
const api = {
  request: (url, options) => request(url, options),
}
```

## Тип теста падает из шва

Тип не выбирается. Сначала называется шов, дальше тип определён однозначно.

Шов это место, где живёт публичный интерфейс, то есть точка, в которой поведение наблюдаемо снаружи. Швы называются и согласуются в [grill](../grill/SKILL.md) до первого теста, там же лежат правила их выбора.

| Где поведение наблюдаемо на этом шве | Форма теста |
| --- | --- |
| вход и выход функции, зависимостей нет | [unit-tests](./unit-tests/SKILL.md) |
| компонент, страница или модуль вместе со своими реальными зависимостями | [integration-tests](./integration-tests/SKILL.md) |
| только приложение, запущенное целиком | [e2e-tests](./e2e-tests/SKILL.md) |

Эти три папки описывают, как писать тест такой формы. Решение принимается не в них, а на шве.

Два следствия, которые стоит держать в голове.

Интерфейс это и есть тестовая поверхность. Вызывающий код и тест пересекают один и тот же шов. Захотелось проверить что-то за интерфейсом, значит модуль неправильной формы, и правильный ход это менять модуль, а не пробираться в него тестом.

Шов сам себя не оправдывает. Один адаптер означает шов гипотетический, два означают настоящий. Заводить шов только ради того, чтобы стало удобнее тестировать, это индирекция, а не проектирование.

## Имена и расположение

Тест лежит рядом с модулем, который проверяет. Зеркальное дерево расходится с кодом при первом же переносе файла, и расхождение никто не замечает.

Имя теста это предложение про поведение, читаемое вслух без кода: «корзина показывает сумму со скидкой», «форма не отправляется с пустым email», «повтор не уходит после ответа 400». Не «test cart», не «работает правильно», не имя функции.

Внутри теста три блока, разделённые пустой строкой: подготовка, действие, проверка. Комментарии-заголовки не нужны, блоки видно глазами. Больше трёх блоков значит в тесте два теста.

## Сколько тестов писать

Список случаев приходит из grill, а не придумывается после кода. Каждый названный случай это один тест на согласованном шве.

| Условие | Что требуется |
| --- | --- |
| всегда | изменение проверено на реальном поведении |
| grill назвал случаи | тест на каждый названный случай |
| было опровержение | тесты на границы и тест, воспроизводящий сценарий отката |

Подробнее в [coverage](./coverage/SKILL.md).
