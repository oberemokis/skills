# Bug hunting

> Точка входа: [skills/core](../../core/SKILL.md). Общие правила тестов: [skills/test](../SKILL.md).

Порядок жёсткий, каждый шаг вперёд только после предыдущего.

1. построить цикл, который ловит баг
2. воспроизвести и минимизировать
3. выдвинуть гипотезы и показать их
4. инструментировать по одной переменной
5. починить и закрепить тестом
6. убрать за собой

Шаг первый несёт непропорционально много веса, и на него уходит непропорционально много усилий. Это не подготовка к работе, это и есть работа.

## Цикл обратной связи

Цикл это команда, которая падает из-за бага и зеленеет без него. Одна команда, запускаемая сколько угодно раз, без участия человека.

Пока такой команды нет, кода не читай. Чтение кода до цикла даёт теорию, которую нечем проверить, а теория, применённая к коду, оставляет второй баг рядом с первым.

Цикл это продукт, а не расходник. Построив, точи его по трём осям: быстрее (секунды, не минуты), резче (проверка указывает на конкретное значение, а не на «упало»), детерминированнее (десять прогонов дают десять одинаковых результатов).

Способы построить цикл, от самого дешёвого к самому дорогому, лежат в [FEEDBACK-LOOP.md](./FEEDBACK-LOOP.md). Бери первый, который достаёт до бага, а не самый мощный.

```bash
# хорошо: одна команда, узкая проверка, повторяемо
pnpm vitest run rates.test.ts -t "сумма приходит числом"
```

```bash
# плохо: ни падения, ни проверки, результат читают глазами
pnpm dev
```

Стоп-условие: цикл построить нечем. Тогда останавливайся и скажи, что нужно, доступ к окружению, дампы, логи с продакшена, разрешение поставить инструментирование. Не подменяй отсутствующий цикл разглядыванием кода: это выглядит как работа и ей не является.

## Воспроизвести и минимизировать

Прогони цикл и убедись, что падение то самое. Симптом обязан совпасть с тем, о чём сообщили: не «тоже красное», а тот же текст, то же значение, то же место.

Дальше выкидывай. Убирай из воспроизведения по одному элементу: поле из запроса, шаг из сценария, запись из данных, флаг из конфигурации. Убрал, а падение осталось, значит элемент был лишний. Падение пропало, значит элемент несущий, возвращай.

Минимизация окончена, когда каждый оставшийся элемент несущий. Это и есть описание бага, гораздо точнее любой формулировки словами.

```ts
// хорошо: осталось только несущее, три поля из сорока
const order = { total: "1200", currency: "RUB", createdAt: "2026-08-25" }
```

```ts
// плохо: воспроизведение тащит весь ответ сервера целиком
const order = await fetchOrderFixture("real-order-dump.json")
```

Второй случай прячет причину: непонятно, какое из сорока полей ломает разбор, и через месяц никто не поймёт, зачем в тесте дамп.

## Гипотезы

От трёх до пяти, ранжированные по правдоподобию, и каждая опровергаема. Опровергаема значит, что к ней приложен признак, который её убьёт.

Меньше трёх означает, что ты уже выбрал ответ и ищешь подтверждение. Проверка одной гипотезы почти всегда обходится дешевле, чем починка не того места.

Список показывается пользователю до проверки, тем же форматом, что раунд в [grill](../../grill/SKILL.md):

```
H1. Схема ответа не валидируется, сумма приходит строкой
    Убьёт: в логе запроса сумма числом

H2. Валидация есть, но приводит тип молча
    Убьёт: в схеме нет coerce и нет transform

H3. Сумма портится позже, при пересчёте скидки
    Убьёт: до пересчёта значение уже строка
```

Порядок в списке это ставка, и она бывает неверной. Пользователь видит то, чего не видишь ты: что вчера меняли схему, что на прошлой неделе такое уже было.

## Инструментировать

По одной переменной за раз. Меняешь две, и результат не относится ни к одной.

Отладчик и точечная вставка лучше сплошного логирования. «Залогировать всё и грепать» это отказ от гипотезы в пользу надежды: вывода становится столько, что в нём тонет тот самый признак.

Отладочные вставки помечай уникальным тегом, по которому их потом найдёшь и снимешь.

```ts
// хорошо: тег уникален, вставка снимается поиском по нему
console.log("[bug-rates]", typeof order.total, order.total)
```

```ts
// плохо: найти и снять нечем, а в выводе не отличить от рабочих логов
console.log(order)
```

### Сужать, а не расширять подмены

Интеграционный тест падает широко и не говорит, где сломалось. Соблазн подменить половину цепочки, чтобы понять, что происходит. Так делать нельзя: мок, добавленный ради диагностики и оставшийся в коде, превращает тест в проверку самого себя.

Сужай иначе. Вызови спорный участок напрямую, отдельно от цепочки, и проверь на тех же данных. Ответ либо здесь, либо участок чист, и тогда переходи к следующему.

По длинной цепочке ищи делением: проверь середину, отбрось половину, повтори. Пять шагов покрывают цепочку из тридцати звеньев.

## Починить и закрепить тестом

Тест пишется до починки. Он падает, и падает по той же причине, что баг.

Тест, написанный после починки, проверяет, что код делает то, что делает. Второй раз этот баг он не поймает, а именно повторное появление и стоит дороже всего.

Тест на баг называется по поведению, а не по номеру задачи: «повтор не уходит после ответа 400», а не «фикс бага 112».

### Правильный шов

Тест ставится на том шве, который достаёт до бага. Форма теста от этого и зависит: где-то это чистая функция, где-то цепочка модулей, где-то запущенное приложение целиком.

Правильный шов это тот, где тест воспроизводит настоящий механизм бага так, как он возникает на месте вызова. Если единственный доступный шов слишком поверхностный, юнит-тест там, где баг проявляется только на цепочке, или тест на одного вызывающего там, где нужно несколько, регрессионный тест даёт ложную уверенность. Он зелёный, а баг живой.

Если правильного шва нет вообще, это само по себе находка, и она важнее самой починки. Значит архитектура не позволяет запереть этот баг. Не пиши тест на поверхностном шве, чтобы закрыть галочку. Назови отсутствие шва вслух, починку сделай, а невозможность закрепить её тестом зафиксируй отдельным пунктом: это работа по изменению формы модуля, и она пойдёт через [grill](../../grill/SKILL.md) как отдельная задача.

### Причина, а не симптом

Записывай и чини причину. «Добавил проверку на undefined» это симптом, «сумма приходила строкой, потому что схема ответа не валидируется» это причина.

Симптом лечится в одном месте и всплывает в трёх других. Признак, что ты поймал симптом: починка выглядит как проверка на пустое значение в месте, где пустого значения быть не должно.

## Убрать за собой

Четыре пункта, и все обязательные.

Прогони исходный сценарий, тот самый, о котором сообщили, а не только свой минимизированный.

Убедись, что регрессионный тест зелёный, и что до починки он был красным. Второе проверяется откатом починки, а не памятью.

Сними отладочные вставки поиском по тегу и верни тест в исходный вид. Диагностические правки в коде не остаются.

Причину запиши в сообщение коммита. Через месяц она понадобится, а восстанавливать её будет неоткуда, правила в [git/commit](../../git/commit/SKILL.md).

## Баг вернулся

Значит теста на него не было, либо тест был, но проверял не то. Разбирайся с этим прежде, чем чинить второй раз: иначе будет третий.

Проверь также, не удалял ли кто тест как «падающий» или «флакающий». Это частый способ вернуть себе старый баг.

## Когда возвращаться в grill

Объём работы задаёт не баг, а его причина. Причина локальна, чини и закрывай. Причина в неверной модели данных или в чужом контракте, останавливайся: сработало условие, которого в начале не было, и надо вернуться в [grill](../../grill/SKILL.md) за вариантами и опровержением. Порядок возврата описан в [core](../../core/SKILL.md).

## Антипаттерны

### Работа без цикла

```ts
// плохо: теория из чтения кода, проверять нечем
// «похоже, тут гонка» -> правка -> «вроде не воспроизводится»

// плохо: воспроизведение руками, десять кликов на каждый прогон
// открыть страницу, войти, выбрать заказ, нажать пересчёт, посмотреть

// плохо: сплошное логирование вместо гипотезы
console.log(JSON.stringify({ order, user, cart, settings }))
```

### Диагностика, оставшаяся в коде

```ts
// плохо: мок появился ради сужения и остался, тест теперь проверяет себя
vi.mock("./rates", () => ({ getRate: () => 1 }))

// плохо: вставка без тега, снять её можно только глазами
console.log("here", order.total)
```

### Прочее

| Не так | Так | Почему |
| --- | --- | --- |
| одна гипотеза и сразу правка | от трёх, ранжированных, с признаком опровержения | одна гипотеза это выбранный ответ, а не разбор |
| две переменные за один прогон | по одной | результат не относится ни к одной из них |
| «не воспроизводится» как вывод | поднять частоту повторами и нагрузкой | редкое падение это тоже падение, см. референс |
| регрессионный тест после починки | до починки, красным | иначе он проверяет код, а не баг |
| дамп ответа целиком в воспроизведении | минимизировать до несущего | причина прячется среди сорока полей |
| номер задачи в имени теста | поведение словами | номер стареет вместе с трекером |
| секрет из перехваченного трейса в фикстуре | подставить `<REDACTED>` | фикстура уезжает в git навсегда |
