# Цикл обратной связи

Открывается из [bug-hunting](./SKILL.md), с первого шага, когда непонятно, чем ловить баг.

Цикл это одна команда, которая падает из-за бага и зеленеет без него. Ступени ниже идут от самой дешёвой к самой дорогой. Бери первую, которая достаёт до бага, а не самую мощную: дорогой цикл на месте дешёвого замедляет каждый следующий прогон.

Инструменты названы, но их API здесь нет, он лежит в `stack`.

## Шесть ступеней

### 1. Падающий тест

Дешевле всего и точнее всего. Годится, когда баг достаётся вызовом кода: разбор данных, вычисление, состояние стора, поведение компонента.

```bash
pnpm vitest run rates.test.ts -t "сумма приходит числом"
```

Флаг `-t` сужает прогон до одного случая, и цикл идёт секунды вместо минут. Конфигурация и проекты в `vitest`, форма теста от шва в [test](../SKILL.md).

### 2. Запрос к поднятому серверу

Годится, когда баг живёт на серверном роуте: разбор тела, заголовки, коды ответа, кеш, правила роутов.

```bash
curl -sS -X POST localhost:3000/api/orders/1/recalc \
  -H 'content-type: application/json' \
  -d '{"total":"1200"}' | jq .
```

Держи такой запрос файлом в репозитории, а не в истории терминала. Иначе цикл живёт до закрытия окна. Про сами роуты и обработчики в `nitro`.

### 3. Прогон по фикстурам со сравнением снимка

Годится, когда вход большой, а выход надо сравнивать целиком: миграции, генераторы, кодогенерация, разбор ответов внешнего сервиса.

Фикстура на входе, снимок на выходе, расхождение и есть падение. Если такой прогон нужен не один раз, заведи его задачей в `turbo`: тогда у него появятся объявленные входы, и кеш перестанет врать.

### 4. Браузерный прогон в headless

Годится, когда баг проявляется только в браузере: гидратация, порядок событий, фокус, перерисовки.

```bash
pnpm playwright test recalc.spec.ts --headed=false --repeat-each=1
```

Дороже предыдущих в разы, поэтому спускайся сюда, только когда первые три до бага не достают. Отладка через терминал и трейсы в `playwright`.

### 5. Минимальный стенд

Отдельный файл или пакет, который воспроизводит только путь бага и ничего больше. Годится, когда баг тонет в приложении: слишком много состояния, слишком долгий запуск, слишком много совпадений.

Стенд отличается от теста тем, что его не обязательно оставлять. Это инструмент на время охоты, и после починки он либо превращается в регрессионный тест, либо удаляется. Третьего не бывает: стенд, оставленный «на всякий случай», через месяц не запускается ни у кого.

### 6. Стенд, который делит сам

Скрипт, перебирающий данные или состояние и находящий границу, за которой падение появляется. Годится, когда воспроизведение зависит от одного значения из большого набора и перебирать его руками дорого.

Границу ищи делением, а не перебором подряд: тридцать звеньев закрываются пятью прогонами.

## Чего здесь нет

Три способа из общей практики к этому стеку пока не привязаны, поэтому примеров под них нет: воспроизведение перехваченного сетевого трейса в отрыве от приложения, property-based и фаззинг для редких падений, дифференциальный прогон одного входа на двух версиях или конфигурациях. Понадобится, пиши по документации инструмента, а не по этому файлу.

## Падение недетерминированное

Редкое падение это тоже падение, и «не воспроизводится» не вывод, а состояние цикла.

Поднимай частоту, пока падение не станет надёжным. Три рычага: повторять прогон много раз подряд, гонять параллельно в несколько процессов, добавлять давление (задержки, нагрузку, сужение таймаутов, случайный порядок случаев).

```bash
# повторяем один случай, пока не поймаем
pnpm vitest run recalc.test.ts -t "пересчёт" --repeat-each=50
```

Частота выросла до предсказуемой, значит цикл готов, и дальше обычный порядок. Частота не выросла ни от одного рычага, значит дело не в гонке, а в данных или в окружении, и искать надо разницу между твоей средой и той, где баг видели.

Отдельно: не помечай тест как флакающий, чтобы он перестал мешать. Так возвращают себе старый баг, и в [bug-hunting](./SKILL.md) про это сказано прямо.

## Секреты в перехваченных данных

Данные из реального окружения приезжают вместе с токенами, ключами и персональными данными. Фикстура уезжает в git навсегда, и вычистить её потом уже нельзя.

Значение заменяй на `<REDACTED>` прямо при сохранении, а не потом. Всё, что нужно по-настоящему, держи в переменных окружения и подставляй на запуске.

```ts
// хорошо: форма сохранена, секрета нет
const captured = { authorization: "<REDACTED>", orderId: 1, total: "1200" }
```

```ts
// плохо: токен уехал в репозиторий вместе с фикстурой
const captured = { authorization: "Bearer eyJhbGciOi...", orderId: 1 }
```

Если для воспроизведения секрет всё-таки необходим, это стоп-условие из [bug-hunting](./SKILL.md): скажи, что нужен доступ, и не сохраняй его в файл.
