# Unit tests

> Точка входа: [skills/core](../../core/SKILL.md). Общие правила тестов: [skills/test](../SKILL.md).

Эта форма выбирается не здесь. Форма падает из шва, который согласован в [grill](../../grill/SKILL.md), а таблица соответствия лежит в [хабе](../SKILL.md). Здесь про то, как писать тест, когда шов оказался на функции без зависимостей.

Юнит-тест означает тест на код без зависимостей, а не тест с подменёнными зависимостями. Разница принципиальная. Первый проверяет логику напрямую, второй проверяет, что ты правильно расставил моки.

## Когда шов оказывается здесь

Признак один: у кода много входов, один выход и нет обращений наружу. Формула расчёта, парсер, валидация, нормализация данных, таблица переходов автомата.

Второй признак, количественный: перебор вариантов через цепочку стоил бы десятков тестов на более высоком шве. Скидка, у которой восемь правил, через интерфейс требует восьми рендеров, а напрямую восьми строк таблицы.

## Когда юнит это сигнал, а не решение

Если для юнита приходится подменять свои модули, останавливайся. Это не юнит, и подмены не спасут. Варианта два: либо тест должен быть [интеграционным](../integration-tests/SKILL.md), либо логика слиплась с вводом-выводом и её надо вынести.

Вынести означает: чистая функция принимает данные и возвращает данные, а всё, что ходит в сеть и в сторы, остаётся снаружи. После этого юнит пишется без единой подмены, а интеграционный тест проверяет, что функцию вызывают в нужном месте.

## Как писать

Табличные случаи, а не десять почти одинаковых тестов. Имя случая складывается из значений, поэтому из отчёта сразу видно, какая комбинация упала.

```ts
describe('applyDiscount', () => {
  test.each([
    [1000, 'SALE10', 900],
    [1000, 'EXPIRED', 1000],
    [0, 'SALE10', 0],
    [1000, '', 1000],
  ])('сумма %i с кодом %s даёт %i', (sum, code, want) => {
    expect(applyDiscount(sum, code)).toBe(want)
  })
})
```

Границы обязательны: пусто, ноль, один, максимум, отрицательное, дубликат, значение на самой границе условия. Ошибки живут именно там, а не в середине диапазона.

## Чего не делать

Не пиши юнит на обёртку без логики: он повторяет реализацию строка в строку.

Не тестируй приватные функции. Если приватную логику хочется проверить отдельно, она либо достаточно важна, чтобы стать публичной, либо проверяется через того, кто её вызывает.

Не проверяй в юните то, что уже покрыто типами. Компилятор дешевле теста.
