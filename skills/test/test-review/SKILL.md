# Test review

> Точка входа: [skills/core](../../core/SKILL.md). Общие правила тестов: [skills/test](../SKILL.md).

## Чеклист

Проходи по порядку, каждый пункт отвечается да или нет:

1. Из имени теста понятно, что именно сломается, если он упадёт
2. Тест стоит на согласованном шве, а не залезает за интерфейс
3. Тест переживёт переписывание внутренностей модуля
4. Утверждение говорит про результат, а не про то, что какой-то метод был вызван
5. Ожидаемое значение пришло из независимого источника, а не пересчитано так же, как его считает код
6. Проверка идёт через тот же интерфейс, которым пользуется вызывающий код, а не через сторонний канал
7. Подменено только то, что выходит за пределы процесса
8. Тест не зависит от других тестов и от порядка запуска
9. Тест проходит в одиночку и проходит дважды подряд
10. У теста есть случай на границу, а не только на середину диапазона

Любое «нет» это не замечание к стилю, а причина переписать тест.

## Порядок починки

Ревью набора тестов даёт десятки находок сразу, и без порядка чинят то, что попалось первым. Порядок задаётся последствием, а не тем, насколько находка раздражает.

Прежде всего отдели то, что вообще не про тесты. Тест упал, поведение изменилось не намеренно, значит ты нашёл дефект продукта. Он обгоняет весь список и уходит в [bug-hunting](../bug-hunting/SKILL.md), а правка ожидания его спрячет.

Остальное сортируется двумя вопросами.

Может ли этот тест быть зелёным, пока поведение сломано? Может уже сейчас, это первый уровень. Сейчас нет, но при будущей поломке не покраснеет, второй.

Может ли он покраснеть, когда ничего не сломано? Тогда третий.

Ни то ни другое, четвёртый.

| Уровень | Последствие | Что сюда попадает |
| --- | --- | --- |
| 1 | зелёный прогон не гарантирует ничего, и об этом не знают | тавтология, ожидание под текущее поведение, снапшот с текущего поведения, подменённый свой модуль, `if` внутри теста, пропущенный тест |
| 2 | поломка придёт и тест её не заметит | поверхностный шов, проверка вызова вместо результата, нет случая на границу |
| 3 | красное перестают читать | флак, зависимость от порядка, общее состояние, `sleep`, проверка через сторонний канал |
| 4 | труднее читать | имя, структура, дублирование подготовки |

В столбце примеры, а не полный список. Находки, которых там нет, сортируются теми же двумя вопросами, включая те, что относятся к порядку работы, а не к самому тесту: тест, дописанный после кода, повторяет код вместе с его ошибкой и потому идёт в первый уровень.

Чинить сверху вниз. Четвёртый уровень законно не починить никогда.

Одно исключение из порядка: если падения в этом наборе уже начали игнорировать, третий уровень идёт раньше второго. Пока красное ничего не значит, первые два уровня неотличимы от зелёного.

### Уровень без доказательства не ставится

У каждой находки называется пункт чеклиста или раздел, из которого она взялась. Иначе уровень это мнение, а спорить с мнением нечем.

```
1. tests/cart.test.ts:14, тавтология
   Ожидание пересчитано тем же reduce, что в calculateTotal, пункт 5.
   Разойтись с кодом не может никогда. Заменить на литерал.

3. tests/orders.test.ts:31, сторонний канал
   Результат читается select-ом в обход getOrder, пункт 6.
   Упадёт при переименовании колонки, хотя поведение не менялось.
```

```
плохо: уровень назван, доказательства нет, действия нет

1. cart.test.ts, плохой тест
2. orders.test.ts, стоит переписать
```

Баллы тесту не ставятся, и общая оценка набора не выводится. Приоритет отвечает на вопрос, что брать следующим, а не на вопрос, насколько всё плохо.

## Тавтологический тест

Самый коварный вид плохого теста: он проходит по построению и никогда не сможет разойтись с кодом.

```ts
// плохо: ожидание пересчитано тем же способом, каким считает код
test('calculateTotal складывает позиции', () => {
  const items = [{ price: 10 }, { price: 5 }]
  const expected = items.reduce((sum, item) => sum + item.price, 0)

  expect(calculateTotal(items)).toBe(expected)
})
```

```ts
// хорошо: ожидание это независимый литерал
test('calculateTotal складывает позиции', () => {
  expect(calculateTotal([{ price: 10 }, { price: 5 }])).toBe(15)
})
```

Ожидаемое значение обязано приходить из источника, независимого от реализации: известный литерал, разобранный руками пример, требование из grill. Сюда же попадают снапшоты, снятые с текущего поведения, и утверждения, где константа сравнивается сама с собой.

## Проверка через сторонний канал

Тест обошёл интерфейс и полез смотреть результат туда, куда вызывающий код не смотрит.

```ts
// плохо: результат читается в обход интерфейса
test('createUser пишет в базу', async () => {
  await createUser({ name: 'Алиса' })

  const row = await db.query('select * from users where name = ?', ['Алиса'])
  expect(row).toBeDefined()
})
```

```ts
// хорошо: результат читается тем же интерфейсом
test('созданного пользователя можно получить', async () => {
  const user = await createUser({ name: 'Алиса' })

  expect((await getUser(user.id)).name).toBe('Алиса')
})
```

Второй вариант проверяет то, ради чего функция существует. Первый закрепляет схему таблицы и упадёт при переименовании колонки, хотя поведение не менялось.

## Правка ожидания это красный флаг

Тест упал, и хочется поменять ожидаемое значение. Сначала ответь на вопрос: поведение изменилось намеренно?

Да, намеренно, тогда правка ожидания законна, но заодно проверь, что тест всё ещё описывает то, что нужно, а не то, что получилось.

Нет, ненамеренно, тогда ты только что нашёл дефект, и правка ожидания его спрячет. Иди в [bug-hunting](../bug-hunting/SKILL.md).

Непонятно, тогда это худший случай: тест не описывает поведение достаточно ясно, чтобы на вопрос можно было ответить. Такой тест переписывается.

## Тест, который страшно менять

Признак такой: тест падает при рефакторинге, который не менял поведение. Ожидания в нём подгоняли уже не раз, и теперь непонятно, что он проверяет.

Не чини его, переписывай. Сформулируй наблюдаемое поведение словами, напиши тест на него, старый удали. Подгоняя ожидания под новый код, ты превращаешь тест в запись того, что код делает, вместо того, что он должен делать.

Удалить тест страшнее, чем оставить, но оставленный врущий тест дороже: он даёт зелёный прогон и при этом ничего не гарантирует.

## Антипаттерны

| Не так | Так | Почему |
| --- | --- | --- |
| проверять, что подмена была вызвана | проверять результат, который увидит пользователь | вызов это реализация, результат это поведение |
| подменить свой модуль, чтобы тест позеленел | оставить реальным и починить причину | зелёный тест на подменённом коде не проверяет ничего |
| ждать через `sleep` | управляемые часы или ожидание условия | тест либо флакает, либо тормозит, а обычно и то и другое |
| один тест на весь сценарий с десятью проверками | тест на шаг, имя равно диагнозу | из отчёта не видно, что упало |
| снапшот вместо явного утверждения | назвать ожидаемое значение | снапшоты обновляют не читая |
| общее мутируемое состояние между тестами | своё состояние на каждый тест | порядок тестов становится значимым, падения плавают |
| тест дописан после кода, чтобы был | случай назван в grill, тест написан на него | тест после кода повторяет код вместе с его ошибкой |
| закомментированный или пропущенный тест | удалить или починить | пропущенный тест это ложный сигнал зелёного прогона |
| условие внутри теста (`if`, `try`) | отдельный тест на каждую ветку | тест с ветвлением проходит, не проверив ничего |
| ожидание пересчитано как в коде | независимый литерал или разобранный пример | тавтология проходит по построению и никогда не спорит с кодом |
| результат прочитан в обход интерфейса | чтение тем же интерфейсом, что у вызывающего кода | сторонний канал закрепляет внутренности, а не поведение |
| все тесты написаны до реализации | один тест, одна реализация, повтор | массовые тесты проверяют воображаемое поведение |
