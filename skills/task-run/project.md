# Папка проекта

Всё, что зависит от проекта, лежит у пользователя вне репозитория: `~/.local/state/task-run/<проект>/`. Ядро скилла не знает ни трекера, ни код-хоста, ни команд проверок.

- `project.json`: данные, схема `schemas/project.schema.json`.
- `rules.md`: правила прозой и глаголы.
- `tasks/<ID>.json`: состояние задач, [state.md](state.md).

Проект узнаётся по `origin`: `scripts/resolve-project.mjs` нормализует адрес и ищет его в `remotes` всех `project.json`. Корень проекта это родитель общего `.git`, поэтому основная папка и все worktree дают один и тот же проект.

## project.json

- `remotes`: адреса origin без схемы, логина и `.git`.
- `taskId`: регулярное выражение ID задачи; `branch`: шаблон ветки с `{id}`; `base`: база по умолчанию; `commit`: шаблон первой строки коммита с `{id}` и `{summary}`.
- `tracker` и `codeHost`: `kind`, `check` (как проверить подключение) и любые данные проекта, на которые ссылаются глаголы: статусы, поля, люди, ID проекта, шаблон MR.
- `worktree`: `dir` (папка worktree в корне, по умолчанию `.worktrees`), `localFiles` (что скопировать из основной папки, если нет), `install` (команды установки с папкой запуска), `exclude` (что дописать в `.git/info/exclude`).
- `checks`: области кода, у каждой `paths` (glob) и `run` (команды по одной), `background` для долгих.
- `review`: области ревью, `with` (скилл `review` или встроенный `code-review`) и `root` для `code-review`.
- `stand`: порт, папка и команда dev-сервера, `null`, если стенда нет.
- `agent`: агент сессий `work` по умолчанию (`claude`, `codex`, `opencode`); поля нет, значит `claude`. Опросник его не спрашивает, поле правится руками.

## rules.md

Обязательные разделы, ядро ссылается на них по именам:

- «Глаголы трекера»: прочитать задачу; задача готова к работе и твоя; начал работу; приостановил; задать вопрос продукту; оставить комментарий; перевести после доставки (по базе); поправить описание.
- «Глаголы код-хоста»: найти MR по ветке; открыть MR; ждать пайплайн MR; ждать пайплайн по SHA; влить MR.
- «База»: как выбрать базу и способ доставки (`mr`, `push` или `local`, когда коммит остаётся в ветке задачи без push и MR), что делать с уже существующей веткой.
- «Документы»: где документ эпика или фичи и что туда пишется.
- «Инструкции репозитория»: какие правила `CLAUDE.md` и `AGENTS.md` проекта этот маршрут не применяет и почему.

Необязательные: «Проверки» (рецепты сверх команд), «Стенд», «Вопрос продукту» (кто читает и как писать).

## Подключения

Каждый вызов проверяет `tracker.check` и `codeHost.check`. Не отвечает: сессия называет, что сломано, и даёт команду, которую пользователь запускает сам. Токены через чат не проходят: набранный в чате токен остаётся в транскрипте. Пример ответа: «MCP трекера не подключён. Добавь его командой `claude mcp add …`, токен положи в переменную окружения, потом повтори вызов».

## Опросник

Запускается, когда папки проекта нет, когда `project.json` не прошёл схему или подключение не отвечает (тогда только по сломанной части), и по `--setup`. С данными в порядке вопросов нет.

1. Собери сам всё, что можно узнать:
   - из репозитория: `origin`, `CLAUDE.md`, `AGENTS.md`, `README`, lock-файлы, шаблоны MR или PR, скрипты проверок, принятые имена веток и формат коммитов в `git log`;
   - из трекера: кто ты, поля и статусы проекта, формат ID;
   - из код-хоста: ID проекта, твой ID, вход в CLI.
2. Спроси только то, чего нигде нет: кто отвечает на вопросы продукту, кто ревьюер, какой статус ставить после доставки, на каком порту стенд. Вопросы по правилам раздела «Вопросы и ожидание» скилла, варианты из найденного.
3. Покажи `project.json` и `rules.md` целиком одним вопросом. Записывай после «да»: `project.json` через `check-json.mjs --commit`, `rules.md` записью файла.
4. Проверь подключения ещё раз и только потом переходи к задачам.
