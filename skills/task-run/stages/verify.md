# Этап verify: автотесты

Сразу после реализации и после каждого круга исправлений.

1. Области диффа: файлы `git diff --name-only <точка>`, где точка это `node <папка скилла>/scripts/fingerprint.mjs --point <база> <worktree>`, плюс новые из `git status --porcelain`, сопоставленные с `paths` в `checks` из `project.json`.
2. Объём по уровню: на S затронутые проверки, на M затронутый набор целиком, на L все области.
3. Команды по одной, не параллельными скриптами менеджера пакетов: параллельные скрипты дерутся за установку зависимостей. Рецепты из раздела «Проверки» в `rules.md` перекрывают команды.
4. Область с `background: true` запускай фоном и жди уведомления. Ожидание чужого прогона под машинным локом не попытка и не красное.
5. Зелёное определяй по выводу (ошибки типов, `FAIL`, число прошедших), а не по коду выхода пайпа. В контекст бери сводку, не лог целиком.
6. Красный тест без понятной причины: `bug-hunting`. Править ожидание без причины нельзя.
7. Красный по вине диффа: чини код. Две попытки не помогли: `blocked` со списком упавших.
8. Результаты в файл задачи, когда всё зелёное. Отпечаток `node <папка скилла>/scripts/fingerprint.mjs <база> <worktree>` снимается после прогона, и если правок за прогон не было, он тот, на котором прогон шёл. Каждому случаю из `context.cases` поле `result`: `status` (`pass`, `fail`, `not_run`, `not_applicable`), `diff` (отпечаток), `at`, `check` (команда, которая проверила именно этот случай). `not_run` и `not_applicable` только с `note`: почему не запускался и почему неприменим. Отсутствие ключей, доступа или данных не делает случай неприменимым, это `not_run`. Отпечаток всего прогона в `verifiedDiff`.

Правка после прогона меняет отпечаток, и прежний `pass` перестаёт быть текущим: он остаётся в файле историей, а этап повторяется. Название команды не доказательство: зелёное читай по выводу, как в шаге 5.

Итог: команды с результатом, числа прошедших и упавших для текста закрытия, случаи не в `pass` с причиной.
