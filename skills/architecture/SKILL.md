# Architecture

> Точка входа: [skills/core](../core/SKILL.md). Если core ещё не прочитан, прочитать его до этого скилла.

Выведено из `ad-tune`. Пакетный менеджер pnpm, задачи через turbo, приложения на Vite с федерацией модулей, серверная часть на Effect.

## Когда применять

- создаёшь файл или пакет и не уверен, куда его положить
- добавляешь зависимость одного пакета на другой
- код хочется переиспользовать, и надо решить, выносить или дублировать
- разбираешься, почему импорт не резолвится или собирается циклическая зависимость

## Когда НЕ применять

- граф задач и кеширование: это `turbo`
- рабочие пространства, каталоги версий, фильтры: это `pnpm`
- код внутри одного файла: это `typescript`
- сборка приложения: это `vite`

## Слои и направление зависимостей

```
apps/web/*        приложения в браузере: host и ремоуты
apps/api/*        серверные приложения
libs/*            интеграционный слой: middleware
packages/*        инструменты без домена: ui, utils, composables, test
shared/*          домен: schemes, config, stores, api, mocks
```

Зависимости идут только вверх по этому списку. Приложение знает про общее, общее не знает про приложения. Это единственное правило, нарушение которого ломает всё остальное: цикл в графе пакетов означает, что ни собрать, ни протестировать по отдельности уже нельзя.

Фактическая картина сейчас:

| Пакет | От кого зависит |
| --- | --- |
| `schemes`, `config`, `stores`, `middleware`, `ui`, `utils`, `composables`, `test` | ни от кого |
| `mocks` | `schemes` |
| `api` | `config`, `mocks`, `schemes`, `test`, `utils` |
| `posts-api` | `schemes` |
| `host` | `config`, `middleware`, `stores` |
| `posts` (web) | `api`, `config`, `schemes`, `stores` |

`schemes` это дно. Контракты не зависят ни от чего, поэтому их можно импортировать откуда угодно, не создавая цикла. Новый общий тип идёт туда, а не в пакет, который случайно оказался под рукой.

## Правила

### Куда положить новый код

Спрашивай по порядку, первый подходящий ответ и есть место.

Нужно только одному приложению, значит остаётся в нём. Переиспользование это не цель, а следствие третьего повторения.

Это контракт данных, тип запроса или ответа, значит `shared/schemes`.

Это конфигурация или переменные окружения, значит `shared/config`.

Это состояние, общее между приложениями, значит `shared/stores`.

Это обращение к внешнему миру по контракту, значит `shared/api`.

Это инструмент без знания домена, значит `packages/*`: компонент в `ui`, чистая функция в `utils`, композабл в `composables`, тестовый хелпер в `test`.

Если не подошло ничего, код остаётся там, где написан, до третьего повторения.

```ts
// хорошо: формат цены нужен двум приложениям, это чистая функция без домена
// packages/utils/src/formatPrice.ts
export function formatPrice(amount: number): string {}
```

```ts
// плохо: тип ответа сервера положили в utils, потому что там уже был файл
// packages/utils/src/types.ts
export type PostResponse = { id: number }
```

Второй случай ломает граф: `utils` это инструмент без домена, и контракт в нём заставит зависеть от `utils` всех, кому нужен тип. Место контракта в `shared/schemes`.

### Импорт через границу пакета только по имени

```ts
// хорошо
import { PostSchema } from "@ad-tune/schemes"
import { Button } from "@ad-tune/ui"
```

```ts
// плохо: путь пробивает границу, пакет перестаёт быть пакетом
import { PostSchema } from "../../../shared/schemes/src"
```

Псевдонимов путей в `tsconfig` нет намеренно: пакеты экспортируют исходники, и с `paths` такая раскладка ломается. Резолв идёт через имена рабочих пространств, и этого достаточно.

### Пакеты экспортируют исходники, а не сборку

```json
// хорошо: так объявлены все десять библиотечных пакетов
{ "exports": { ".": "./src/index.ts" } }
```

```json
// плохо: собранный вывод для внутреннего пакета добавляет шаг и ничего не даёт
{ "main": "./dist/index.js", "types": "./dist/index.d.ts" }
```

Следствия, о которых надо знать. Шага сборки у библиотек нет, поэтому правка видна сразу. Но и кеша turbo у них тоже нет: кешируется только то, что производит файлы. И бандлер приложения обрабатывает исходники пакетов сам, а значит настройки приложения на них распространяются.

### Точку входа делят, когда часть кода не должна уехать в браузер

```json
// хорошо: @ad-tune/config
{
  "exports": {
    ".": "./src/index.ts",
    "./client": "./src/client.ts"
  }
}
```

```ts
// плохо: один вход, и серверные секреты попадают в клиентскую сборку
import { config } from "@ad-tune/config"
```

Клиентская часть валидируется на загрузке, чтобы опечатка в переменной падала сразу, а не в середине работы. Это правило шире конфигурации: любой пакет, у которого есть серверная и браузерная половины, разделяет входы, а не полагается на то, что бандлер вырежет лишнее.

### Граница федерации не видна графу пакетов

`host` не зависит от `posts` в `package.json`. Связь появляется только в рантайме, и это меняет три вещи.

Turbo не может упорядочить сборку через `^build`: он читает граф пакетов, а там связи нет.

Типы приходится генерировать. Скрипт `scripts/gen-remotes.ts` читает манифест ремоутов из `@ad-tune/config` и пишет `apps/web/host/src/remotes.d.ts`, реэкспортируя типы из исходников каждого ремоута. Поэтому `import("posts/PostList")` типизирован так же, как сам компонент, без архивов типов и без обращения к сети.

Ремоут может быть недоступен, и это нормальное состояние, а не сбой. Падение ремоута не должно валить хост.

```ts
// хорошо: манифест один, в @ad-tune/config
export const remotes = { posts: { exposes: { PostList: "components/PostList.vue" } } }
```

```ts
// плохо: адрес ремоута вписан в приложение, манифест и код разъезжаются
const PostList = () => import("http://localhost:5174/assets/PostList.js")
```

После правки манифеста нужен `pnpm gen:remotes`, иначе типы отстанут от реальности.

### Состояние, общее между хостом и ремоутами, живёт в shared

`host` и `posts` оба зависят от `@ad-tune/stores`. Это осознанно: состояние, которое видят обе стороны, обязано быть объявлено в одном месте, иначе получится два независимых экземпляра и рассинхрон.

```ts
// хорошо: стор объявлен один раз в shared/stores, оба приложения его импортируют
import { useSessionStore } from "@ad-tune/stores"
```

```ts
// плохо: у каждой стороны свой стор, состояние разъедется в рантайме
// apps/web/host/src/stores/session.ts
// apps/web/posts/src/stores/session.ts
```

Обратная сторона: такое состояние становится контрактом между приложениями. Менять его форму означает править обе стороны одновременно.

### Серверный код делит сервис и репозиторий

```
apps/api/posts/src/
  service.ts       правила
  repository.ts    хранилище
  errors.ts        типизированные ошибки
```

```ts
// хорошо: правило в сервисе, запрос в репозитории
// service.ts
getById: (id: number) =>
  repository.findById(id).pipe(Effect.flatMap(orNotFound(id)))
```

```ts
// плохо: сервис сам ходит в хранилище, подменить границу нечем
// service.ts
getById: (id: number) => sql`select * from posts where id = ${id}`
```

Репозиторий знает про хранилище и ничего про правила. Сервис получает его зависимостью, поэтому в тесте подменяется граница процесса, а не свой модуль. Подробности в `effect`.

## Что в текущей архитектуре стоит починить

Разобрано по фактическому состоянию `ad-tune`.

`shared/api` держит `@ad-tune/mocks` и `@ad-tune/test` в обычных зависимостях, а не в `devDependencies`. Через `apps/web/posts`, который зависит от `api`, тестовая инфраструктура и заглушки попадают в граф зависимостей приложения. Либо перенести в `devDependencies`, либо развести моки в отдельный вход, как сделано с `config`.

`packages/ui`, `packages/utils` и `packages/composables` не зависят друг от друга вовсе. Это либо честная независимость, и тогда всё в порядке, либо в `ui` продублировано то, что уже есть в `utils`. Стоит проверить и решить осознанно.

У `typecheck` в `turbo.json` не объявлены выходы, хотя `composite: true` в восьми пакетных tsconfig заставляет `tsc` писать `.tsbuildinfo`. Это ломает восстановление из кеша, подробности в `turbo`.

## Антипаттерны

### Зависимость не в ту сторону

```json
// плохо: общий пакет знает про приложение
// shared/api/package.json
{ "dependencies": { "@ad-tune/host": "workspace:*" } }
```

```json
// хорошо: приложение зависит от общего, а не наоборот
// apps/web/host/package.json
{ "dependencies": { "@ad-tune/api": "workspace:*" } }
```

Если общему пакету понадобилось что-то из приложения, значит это «что-то» лежит не там: его место в общем пакете, а не в приложении.

### Тестовое в проде

```json
// плохо: моки и хелперы уезжают в граф приложения
{ "dependencies": { "@ad-tune/test": "workspace:*" } }
```

```json
// хорошо
{ "devDependencies": { "@ad-tune/test": "workspace:*" } }
```

### Прочее

| Не так | Так | Почему |
| --- | --- | --- |
| относительный путь через границу пакета | импорт по имени пакета | иначе границы нет и пакет не переносится |
| `paths` в tsconfig для внутренних пакетов | резолв по именам рабочих пространств | с экспортом исходников `paths` ломается |
| выносить в общий пакет на втором повторении | терпеть до третьего | преждевременная абстракция дороже дублирования |
| новый пакет ради одной функции | положить в существующий по смыслу | пакет это граница, а не папка |
| зависимость приложения в корневом `package.json` | в том пакете, который её использует | корневая установка инвалидирует все кеши |
| адрес ремоута в коде приложения | манифест в `@ad-tune/config` | иначе манифест и код разъезжаются |
| правка манифеста ремоутов без `pnpm gen:remotes` | сгенерировать типы | типы отстанут, а ошибка всплывёт в рантайме |
| общий тип в случайном пакете | `shared/schemes` | контракты на дне графа, оттуда их видно всем без цикла |
