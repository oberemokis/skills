# Этап implement: реализация

Вход: `context` из файла, уровень, открытые `findings`, если это круг исправлений.

1. Проверь, что ветка в worktree это ветка задачи. Нет: `blocked`.
2. Скиллы: `test`; фича идёт по `tdd`, баг по `bug-hunting`. Стековые подключает маршрутизация `core`.
3. Фича: цикл `tdd` по одному случаю. Красный тест (запущен и упал по нужной причине), минимум кода до зелёного, рефакторинг на зелёном. Следующий случай только после зелёного. Случаев нет: цикл не нужен.
4. Баг: порядок `bug-hunting` без пропусков.
   - Цикл, который падает из-за бага, до чтения кода. Построить нечем: вопрос, что нужно (доступ, логи, данные).
   - Воспроизведение и минимизация.
   - Гипотезы, от трёх до пяти, с признаком опровержения: вопрос пользователю, гипотезы в `preview`. Выбранную запиши в `hypothesis`.
   - Инструментирование по одной переменной, вставки с тегом.
   - Регрессионный тест на правильном шве, красный до починки. Чинить причину, а не симптом.
   - Уборка: красный до починки проверен откатом, вставки сняты по тегу. Причину одной фразой в `cause`.
5. Круг исправлений: каждый открытый пункт `findings`. С `bug: true` идёт по шагу 4, тест не правится, пока не найдена причина. Остальные: тест, который ловит проблему, потом правка. Исправленный пункт `fixed`, не исправленный остаётся `open` с причиной.
6. Нужен случай или шов вне плана, или сработало условие допроса из `core`: остановись, не дописывая. Вопрос: своё решение с причиной или пауза для `/oberemokis-skills:grill`.
7. Ответ продукта, который влияет на решение, запиши в документ по разделу «Документы». Правку описания задачи здесь не делай, её вносит close.
8. Читай и правь только файлы worktree.
9. Пересмотр уровня: дифф больше 300 строк или 5 файлов, появился контракт или API. Тогда вопрос «Поднять уровень»; поднятие добавляет этапы в `stages`.

Коммита на этом этапе нет. Итог до 10 строк: сделанное по случаям, что осталось, причина бага, размер диффа.
