# Файл задачи

Файл `<папка проекта>/tasks/<ID>.json`, схема `schemas/task.schema.json`. Он хранит решения и прогресс маршрута. Истина о задаче в другом месте, и при расхождении права она, в таком порядке: git и код-хост, затем трекер, файл последним.

## Поля

- `schema`: всегда `task-run/task@1`. `plugin`: версия и папка плагина, на котором начата задача.
- `project`, `task`, `title`, `type` (`feature` или `bug`), `level`, `levelReason`.
- `base`, `delivery` (`mr` или `push`), `branch`, `worktree` (абсолютный путь), `fleet`.
- `session`: имя агента, workspace и панель herdr, ID сессии Claude. Вне herdr первые три `null`. ID сессии Claude бери из `herdr agent get "$HERDR_PANE_ID"` (`agent_session.value`), без herdr `null`.
- `stage`: текущий этап, его состояние (`running`, `waiting-user`, `waiting-external`, `blocked`, `stopped`, `done`), `waiting` одной строкой и `since`. По `stage` оркестратор понимает, что с задачей, не читая экран.
- `stages`: каждый этап один раз, статус и время, короткая `note`. Статус меняется заменой значения.
- `context`: итог этапа start. Цель, критерии приёмки, тестовые случаи со швами, решения, открытые вопросы, документ эпика, имена заметок памяти. Продолжение в новой сессии берёт его отсюда.
- `findings`: находки ревью, аудита, показа и красного пайплайна, со статусом `open`, `fixed` или `accepted`. Пункт с `bug: true` идёт через `bug-hunting`.
- `hypothesis`, `cause`: выбранная гипотеза бага и причина одной фразой для сообщения коммита.
- `fixRounds`: число завершённых кругов исправлений. Растёт, когда круг закончен, а не когда начат.
- `flag`: флаг «в работе» и с какого времени он стоит. Нужен, чтобы при закрытии назвать подозрительный отрезок времени.
- `pending`, `outbound`: намерение внешнего действия и журнал сделанных (раздел «Внешние шаги»).
- `reviewedDiff`: отпечаток диффа, который пользователь одобрил на шаге «Дифф и показ».
- `commit`, `mrs`: SHA коммита задачи и список MR (их бывает больше одного).

## Когда писать

Первый раз в конце этапа start, когда `context` собран. Дальше при каждой смене этапа, перед и после каждого внешнего шага, перед вопросом и после ответа. Запись только через `check-json.mjs --commit`.

## Внешние шаги

Всё, что видят другие (push, MR, слияние, комментарий, статус, вопрос продукту), делается так:

1. Посмотри на мир: не сделано ли это уже. MR по ветке со всеми статусами, влит ли MR, есть ли твой комментарий после `stage.since` с тем же началом текста, нет ли незаконченного rebase или merge.
2. Сделано: допиши в `outbound` и иди дальше, не повторяя.
3. Не сделано: `pending` с действием и временем, запись, действие, затем запись в `outbound` и `pending: null`.

При старте сессии `pending` не пуст: сначала шаг 1. Результат найден: допиши его. Не найден и неясно, ушло ли действие: вопрос пользователю, а не повтор.

## Продолжение

Файл есть, сессия новая (упала прежняя, пользователь вызвал снова, `task-fleet` перезапустил):

1. Проверь файл `check-json.mjs`. Поля пройденных этапов отсутствуют: восстанови из git, код-хоста и трекера, покажи пользователю одним сообщением, запиши.
2. `stage.status = stopped`: спроси, продолжать ли.
3. Обнови `session` своими значениями.
4. Прерванный этап начинается заново. Правки в worktree считаются своими: покажи `git status --short` и diffstat одной строкой в чат и продолжай с них.
5. Внешние шаги проверяй по разделу выше до любого действия.

Файл говорит `close: done`, а задачу вернули в работу: перенеси файл в `tasks/archive/<ID>-<дата>.json` и начни новый круг с этапа start.
