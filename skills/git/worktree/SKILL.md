# Worktree

> Точка входа: [skills/core](../../core/SKILL.md). Если core ещё не прочитан, прочитать его до этого скилла.

Worktree это вторая рабочая копия того же репозитория. Git не знает, где такие копии должны лежать, и без соглашения они расползаются по соседним папкам. Новая копия при этом не получает файлы, которых нет в git, и работает без них молча.

## Когда применять

- нужно создать worktree под ветку
- задача ведётся в отдельном worktree, и надо проверить, что он в порядке
- worktree нужно убрать: ветка закрыта или работа в нём не нужна

## Когда НЕ применять

- обычная работа в основной папке без отдельной ветки: скилл не нужен
- коммит, пуш и ветвление для PR: это скилл `commit` и правила ветвления, сюда они не входят
- разбор конфликтов слияния: см. `mattpocock-skills:resolving-merge-conflicts`
- worktree, созданные вне `.worktrees`: их не переносим и не удаляем, даже если они выглядят устаревшими, а спрашиваем пользователя

## Правила

### Путь всегда внутри .worktrees

Новый worktree создаётся в папке `.worktrees` в корне репозитория, по пути `.worktrees/<имя>`. Имя это имя ветки, где `/` заменён на `-`: ветка `feature/EYE-1278` даёт `.worktrees/feature-EYE-1278`. Папку `.worktrees` создать, если её нет.

Копии рядом с репозиторием не создаём. Такая папка лежит вне корня, не видна в `ls` и через месяц становится загадкой. Плохо: `git worktree add ../repo-feature-x`.

### Папка скрыта от git

Перед созданием первого worktree проверить, что `.worktrees` игнорируется: `git check-ignore -q .worktrees`. Если не игнорируется, добавить строку `/.worktrees/` в `.git/info/exclude`. Это локальный файл, в коммит он не попадает.

В `.gitignore` не писать. Это правка, которую пользователь коммитит сам. Если правило должно быть общим для всех, сказать ему об этом отдельно. Об изменении `.git/info/exclude` тоже сообщить, одной строкой.

### Проверить, что workspace не захватит .worktrees

Если в корне монорепы есть `pnpm-workspace.yaml`, `turbo.json` или конфиг тестов с шаблонами `**`, проверить, не захватывает ли шаблон папку `.worktrees`. Вложенные `package.json` внутри копии могут попасть в сборку и тесты основного репозитория, и тогда ошибка проявляется в чужом прогоне. Если шаблон захватывает папку или ответ неочевиден, остановиться и спросить, как её исключить.

### Копировать локальные файлы, которых нет в git

Новая копия получает только то, что лежит в git. Из основной папки в worktree переносятся:

- `.mcp.json`: без него lean-ctx в worktree не подключён
- `.claude/settings.local.json`: в нём хуки и разрешения
- `.env` и `.env.*`, если они есть: без них приложение не стартует

Переносятся только эти файлы. Игнорируемые `node_modules`, `dist` и кэши не копируются. Если в корне есть другой локальный файл, которого нет в списке, спросить пользователя, нужен ли он в копии.

### Зависимости ставить внутри worktree

Менеджер пакетов выбирается по lock-файлу: `pnpm-lock.yaml` значит pnpm, `package-lock.json` значит npm, `yarn.lock` значит yarn. Установка в основной папке для копии не считается: `node_modules` там не появится, и сборка внутри worktree упадёт.

### Создавать от явной базы

База по умолчанию это основная ветка репозитория. Если пользователь назвал другую базу, брать её. Если ветка с таким именем уже существует, использовать её без создания новой, иначе git откажет.

Перед созданием смотреть `git worktree list`. Если для этой ветки worktree уже есть, работать в нём, а не создавать второй.

### Работать только в своём worktree

Все команды задачи выполняются с путём worktree. Правки в основной папке для задачи из worktree не делаем: две копии расходятся без следа. Перед первой правкой убедиться, что `git -C <путь> status` показывает нужную ветку.

### Удалять через git worktree remove

Удаление только командой `git worktree remove <путь>`, затем `git worktree prune`. Папку через `rm -rf` не удаляем: git продолжит считать worktree живым и будет держать ветку.

Если `git worktree remove` отказал из-за незакоммиченных правок, `--force` самостоятельно не добавляем. Спросить пользователя, что делать с правками: закоммитить, сохранить в stash или выбросить. Решение за ним.

Ветку при удалении worktree не трогаем. Удалять ветку можно только по прямой просьбе.

## Антипаттерны

| Не так | Так | Почему |
| --- | --- | --- |
| `git worktree add ../<имя>` | `git worktree add .worktrees/<имя>` | копия вне репозитория теряется из вида |
| `rm -rf` папки worktree | `git worktree remove`, затем `prune` | git считает worktree живым и держит ветку |
| `--force` при удалении без вопроса | спросить, что делать с правками | незакоммиченная работа исчезает без следа |
| установка зависимостей в основной папке для копии | установка внутри worktree | `node_modules` в копии не появится |
| копирование `node_modules` между папками | установка заново | зависимости с абсолютными путями в другой папке ломаются |
| работа с worktree вне `.worktrees` | спросить пользователя | чужая копия может держать незакоммиченную работу |
| правка `.gitignore` без спроса | `.git/info/exclude` и сообщение пользователю | общий файл коммитит пользователь |
