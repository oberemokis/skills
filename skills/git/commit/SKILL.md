# Commit

> Точка входа: [skills/core](../../core/SKILL.md). Если core ещё не прочитан, прочитать его до этого скилла.

Три запрета здесь жёсткие и не обсуждаются: авторство, атрибуция, хуки. Остальное про то, что попадает в коммит и как он описан.

## Когда применять

- пользователь просит закоммитить
- работа закончена, и её надо зафиксировать
- надо разобрать наработанное на несколько коммитов

## Когда НЕ применять

- пуш, ветки, слияния, разбор конфликтов: сюда не входят
- пользователь не просил коммитить: не коммить по своей инициативе

## Правила

### Автор коммита только пользователь

Данные берутся из `git config`. Ни `--author`, ни переменные окружения `GIT_AUTHOR_*` и `GIT_COMMITTER_*` не трогаются никогда.

```bash
# хорошо
git commit -m "..."
```

```bash
# плохо
git commit --author="Claude <noreply@anthropic.com>" -m "..."
GIT_AUTHOR_NAME="agent" git commit -m "..."
```

### Никакой AI-атрибуции в сообщении

Ни трейлеров, ни упоминаний в теле, ни эмодзи-подписи. История коммитов это история изменений кода, а не журнал того, кто держал клавиатуру.

```bash
# хорошо
git commit -F - <<'MSG'
Кеш ответов курсов валют

Обработчик курсов кешируется на пять минут, ключ задан явно,
иначе он выводится из расположения кода и меняется при переносе.
MSG
```

```bash
# плохо: трейлеры и упоминания инструмента
git commit -m "Кеш курсов

Co-authored-by: Claude <noreply@anthropic.com>
Generated with Claude Code"
```

### Хуки выполняются всегда

`--no-verify` не используется ни при каких обстоятельствах. Хук существует, чтобы поймать то, что человек забыл, и обход хука это способ закоммитить именно ту ошибку, от которой он защищает.

```bash
# хорошо: хук упал, значит сначала починить
git commit -m "..."   # линт не прошёл
pnpm lint --fix
git commit -m "..."
```

```bash
# плохо
git commit --no-verify -m "..."
```

Если хук мешает по существу, его надо править, а не обходить.

### Смотри, что попадает в коммит

После широкого `git add` содержимое индекса читается глазами. Ищи не только лишние файлы, но и подозрительное содержимое в безобидных по имени: токены, ключи, пути с именем пользователя, дампы.

```bash
# хорошо
git add -A
git status --short
git diff --cached
git commit -m "..."
```

```bash
# плохо: коммит вслепую
git add -A && git commit -m "..."
```

### Сообщение объясняет причину, а не перечисляет файлы

Первая строка это результат в одну фразу без точки. Дальше пустая строка и тело, где написано, почему сделано так. Что именно поменялось, видно из диффа, и дублировать это в сообщении незачем.

Хорошо:

```
Кеш ответов курсов валют

Курсы меняются раз в несколько минут, а запрос уходил на каждый рендер.
Ключ кеша задан явно: без имени он выводится из расположения кода
и меняется при переносе файла.
```

Плохо, пересказ диффа вместо причины:

```
Обновил rates.get.ts, добавил defineCachedEventHandler, поправил импорты
```

Номера задач в сообщение не идут: история живёт в git и в трекере, а не в префиксах строк.

### Один коммит это одно изменение

Если в сообщении появляется «и», это обычно два коммита. Разбирай наработанное по смыслу, а не по времени.

```bash
# хорошо
git add skills/stack/vue
git commit -m "Правила Vue: реактивность и ссылки на элементы"

git add scripts
git commit -m "Скрипт пересборки списка скиллов в манифесте"
```

```bash
# плохо
git add -A
git commit -m "Скиллы по Vue и скрипт синхронизации манифеста"
```

## Антипаттерны

| Не так | Так | Почему |
| --- | --- | --- |
| `--author` или подмена `GIT_*` | оставить `git config` | авторство принадлежит человеку |
| `Co-authored-by`, `Generated with` | ничего не добавлять | история про код, а не про инструмент |
| `--no-verify` | починить причину падения хука | обход коммитит именно ту ошибку, от которой хук защищает |
| `--amend` по чужому или запушенному коммиту | новый коммит | перезапись истории ломает её у других |
| `git add -A` без чтения индекса | `git status` и `git diff --cached` | лишний файл замечают уже после пуша |
| коммит по своей инициативе | дождаться просьбы | пользователь решает, когда фиксировать |
| перечисление файлов в сообщении | причина изменения | список файлов и так есть в диффе |
| номер задачи в сообщении | ничего | история живёт в трекере |
| «и» в первой строке | два коммита | одно изменение на коммит |
| `git checkout` и `git reset --hard` при незакоммиченных правках | `git stash -u` либо коммит | несохранённая работа исчезает без следа |
