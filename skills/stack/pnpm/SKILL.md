# pnpm

> Точка входа: [skills/core](../../core/SKILL.md). Если core ещё не прочитан, прочитать его до этого скилла.

Версия: pnpm 11.23.0. Монорепа с раскладкой `apps/api/*`, `apps/web/*`, `libs/*`, `packages/*`, `shared/*`, задачи гоняет turbo.

Версия выше не украшение. Правила про поведение переживают мажорные обновления, а всё из раздела «Привязано к версии» перестаёт быть верным вместе с ней: если в `package.json` версия другая, сверь имена до того, как напишешь.

Поле `packageManager` в `package.json` закрепляет версию, которой ставят зависимости, и она вполне может отстать от той, что стоит в системе. Разошлась с заявленной выше, значит раздел «Привязано к версии» для этого проекта непроверен, а там же лежит порядок обновления.

## Когда применять

- добавляешь, обновляешь, удаляешь зависимости
- правишь `pnpm-workspace.yaml`, добавляешь пакет в монорепу
- настраиваешь CI: установку, кеш, публикацию
- зависимость поставилась, но не работает

## Когда НЕ применять

- граф задач, кеширование сборок, `turbo.json`: это `turbo`
- конфигурация сборки: это `vite`
- конфигурация тестов: это `vitest`

## Правила

### Конфигурация живёт в pnpm-workspace.yaml, ключи в camelCase

`.npmrc` остаётся только для аутентификации. Ключи там были в kebab-case, в `pnpm-workspace.yaml` они camelCase, и механический перенос без переименования молча не применяется.

```yaml
# хорошо: pnpm-workspace.yaml
packages:
  - "apps/api/*"
  - "apps/web/*"
publicHoistPattern:
  - ts-pattern
nodeLinker: isolated
```

```ini
# плохо: .npmrc, ключ не будет прочитан как настройка pnpm
public-hoist-pattern[]=ts-pattern
node-linker=isolated
```

Отдельного `.npmrc` в подпакетах больше нет: пер-пакетные настройки задаются через `packageConfigs` в корневом `pnpm-workspace.yaml`.

### Версии общих зависимостей держи в каталоге

В монорепе одна и та же библиотека расползается по десятку `package.json`. Каталог задаёт версию один раз.

```yaml
# хорошо
catalogs:
  prod:
    vue: ^3.5.41
  dev:
    vitest: ^4.1.11
```

```json
{ "dependencies": { "vue": "catalog:prod" } }
```

```json
// плохо: версия переписана в каждом пакете и разъедется при первом обновлении
{ "dependencies": { "vue": "^3.5.41" } }
```

`catalog:` без имени это `catalog:default`. Протокол работает в обычных, dev, peer и optional зависимостях, в `overrides` и в CLI (`pnpm add vue@catalog:`). При публикации `catalog:` и `workspace:` разворачиваются в реальные версии, так что наружу протокол не утекает.

### Фильтры выбирают по графу, а не по имени

```bash
# хорошо
pnpm --filter web... build          # web и то, что от него зависит
pnpm --filter ...web build          # web и его зависимости
pnpm --filter "...[origin/main]" test   # всё, что изменилось от ветки
```

```bash
# плохо: перечисление руками разъедется с графом
pnpm --filter web --filter shared --filter libs-ui build
```

Направление точек путается легко: точки слева означают зависимости, справа зависимых.

### Скрипты сборки зависимостей не запускаются сами

pnpm не выполняет `postinstall` у зависимостей, пока их явно не разрешили. Это самая частая причина «поставилось, но не работает».

```bash
# хорошо
pnpm approve-builds
```

```bash
# плохо: разрешить всё подряд, чтобы «просто заработало»
pnpm install --dangerously-allow-all-builds
```

Разрешения записываются в `pnpm-workspace.yaml`. В CI они должны быть в репозитории, иначе сборка разойдётся с локальной машиной.

### Скрипт, обязательный во всех пакетах, объявляй явно

```yaml
# хорошо
requiredScripts:
  - build
```

```bash
# плохо: рассчитывать, что прогон упадёт сам
pnpm -r run build   # пакет без скрипта просто пропущен, код возврата нулевой
```

Без этого `pnpm -r run build` тихо пропустит пакет, где скрипта нет, и вы узнаете об этом на деплое.

## Привязано к версии

Изменилось в 11 относительно 10.

| Было в 10 | Стало в 11 |
| --- | --- |
| `onlyBuiltDependencies`, `neverBuiltDependencies`, `ignoredBuiltDependencies` | единая карта `allowBuilds` |
| свежий релиз ставится сразу | `minimumReleaseAge` по умолчанию 1440 минут, то есть сутки |
| подстановка переменных окружения в проектном `.npmrc` работала | отключена |
| несовпадение хеша тарбола предупреждало | фатальная ошибка |
| глобального конфига не было | `config.yaml` |
| `pnpm install --frozen-lockfile` в CI | `pnpm ci` |
| `pnpm config get` только текстом | есть вывод в JSON |

Порядок обновления с десятой версии на одиннадцатую:

1. Поменять `packageManager` на `pnpm@11.23.0` в корневом `package.json` и ту же версию в CI. Если версии разойдутся, локально и в CI соберутся разные лок-файлы.
2. Перенести всё, что осталось в `.npmrc`, в `pnpm-workspace.yaml` в camelCase, после чего `.npmrc` удалить. Например `public-hoist-pattern[]` становится `publicHoistPattern`.
3. Переустановить зависимости и закоммитить лок-файл: формат менялся, диff будет большим.
4. Учесть `minimumReleaseAge`: сутки после публикации пакет не поставится. Если это мешает, задать значение явно.
5. Прогнать `turbo` заново: смена лок-файла инвалидирует все кеши сборок.

## Антипаттерны

| Не так | Так | Почему |
| --- | --- | --- |
| настройки pnpm в `.npmrc` | `pnpm-workspace.yaml` в camelCase | из `.npmrc` они не читаются, и ошибки не будет |
| `.npmrc` в подпакете | `packageConfigs` в корне | пер-пакетные `.npmrc` больше не поддерживаются |
| `npm_config_*` в CI | `pnpm_config_*` или `PNPM_CONFIG_*` | pnpm перестал читать переменные npm |
| одна версия библиотеки в десяти `package.json` | каталог | иначе версии разъезжаются незаметно |
| зависимость приложения в корневом `package.json` | в том пакете, который её использует | корневая установка меняет лок-файл и инвалидирует все кеши turbo |
| общий кеш стора между доверенными и недоверенными задачами CI | разделить | стор это часть модели доверия, а не только ускорение |
| ручное перечисление пакетов в фильтре | фильтр по графу | список разъедется с реальными зависимостями |
| `pnpm publish` без `-r` в монорепе | `pnpm publish -r --no-git-checks` | иначе опубликуется только корень |
