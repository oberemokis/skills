# Реактивность: computed и watch

Читается из [SKILL.md](./SKILL.md), когда значение обновляется не тогда, когда ожидалось, или обновляется лишний раз.

## Тайминги flush

По умолчанию наблюдатель срабатывает до обновления DOM. Симптом выглядит как гонка, и рефлекс подсказывает обернуть в `nextTick`, но правильный ответ это режим сброса.

| Режим | Когда срабатывает | Для чего |
| --- | --- | --- |
| `pre` | до обновления DOM, по умолчанию | реакция на данные, DOM не читается |
| `post` | после обновления DOM | чтение размеров, позиций, фокуса |
| `sync` | на каждую мутацию, без батчинга | почти никогда |

```ts
// хорошо
watch(messages, () => scrollToBottom(), { flush: "post" })
watchPostEffect(() => list.value?.scrollTo(0, list.value.scrollHeight))
```

```ts
// плохо: прочитает высоту до перерисовки
watch(messages, () => list.value?.scrollTo(0, list.value.scrollHeight))
```

`sync` опасен тем, что снимает батчинг: пять мутаций в одном тике дадут пять срабатываний. Если он кажется нужным, скорее всего задача решается через `post`.

Для одноразовой инициализации после монтирования наблюдатель вообще не нужен, достаточно `onMounted`.

## Стабильность ссылки в computed

Начиная с 3.4 подписчики пересчитываются только когда значение изменилось. Но если геттер возвращает новый объект, значение считается новым всегда, даже когда поля внутри те же.

```ts
// хорошо: вернуть прежнюю ссылку, если содержимое совпало
const stats = computed((previous) => {
  const next = { isEven: count.value % 2 === 0 }

  if (previous && previous.isEven === next.isEven) return previous

  return next
})
```

```ts
// плохо: подписчики пересчитываются на каждое изменение count
const stats = computed(() => ({ isEven: count.value % 2 === 0 }))
```

Важная тонкость: вычисление выполняется целиком до сравнения. Ранний возврат `previous` до того, как прочитаны зависимости, ломает их отслеживание, и наблюдатель перестаёт срабатывать вообще.

## Прокси и равенство

`reactive` возвращает прокси, у которого другая идентичность. Сравнение с исходным объектом всегда ложно, и это невидимо: в коде стоит обычный `===`.

```ts
// хорошо: сравнивать по идентификатору
const isSelected = computed(() => selectedId.value === item.id)
```

```ts
// плохо
const state = reactive(original)
state === original // всегда false
```

Та же ловушка в `Set` и `Map` с объектами-ключами: положили исходный объект, ищете по прокси, не находите. `toRaw` снимает обёртку, но чаще правильный ход это не использовать `reactive` там, где хватает `ref`, и сравнивать по полю.

## Отмена и ограничение наблюдателей

```ts
// хорошо: запрос отменяется, когда зависимость поменялась
watchEffect(() => {
  const controller = new AbortController()
  onWatcherCleanup(() => controller.abort())

  void loadPosts(userId.value, controller.signal)
})
```

```ts
// плохо: самодельный флаг отмены, старый ответ всё равно придёт
let isStale = false
watchEffect(() => {
  isStale = true
  void loadPosts(userId.value)
})
```

Глубину обхода можно ограничить числом: `watch(state, callback, { deep: 2 })`. Полный глубокий обход большого дерева стоит дорого, а нужен редко.

Одноразовый наблюдатель объявляется опцией, а не ручным `stop` внутри колбэка: `watch(source, callback, { once: true })`.

## shallowRef и когда он оправдан

Для примитивов `ref` и `shallowRef` ведут себя одинаково, поэтому совет «всегда `shallowRef` для примитивов» бессмысленный.

Он оправдан на больших структурах, которые заменяются целиком: список на тысячу элементов, разобранный документ, ответ сервера. Глубокое отслеживание там стоит заметно, а мутаций внутрь нет.

```ts
// хорошо: список заменяется целиком
const rows = shallowRef<Row[]>([])
rows.value = await loadRows()
```

```ts
// плохо: мутация внутрь не вызовет обновления
const rows = shallowRef<Row[]>([])
rows.value.push(newRow)
```

Второй пример это главная опасность `shallowRef`: код выглядит рабочим и молчит.
