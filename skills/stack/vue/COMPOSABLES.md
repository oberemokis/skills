# Дробление композаблов

Читается из [SKILL.md](./SKILL.md), когда композабл собирает функционал целого экрана и его пора делить на части.

Композабл это единица повторного использования с состоянием, то есть та же задача, которую в ООП решает класс. Приёмы оттуда переносятся почти без изменений, меняется только форма записи.

Наследования в композаблах нет вовсе, поэтому один приём выглядит иначе, чем в классах: роль базового класса берут на себя опции, а роль переопределённого метода играет ветка внутри. Всё остальное переносится буквально.

## Что брать под какую задачу

| Приём | Форма в композабле | Когда брать |
| --- | --- | --- |
| одна ответственность | один источник правды и один набор внешних эффектов | всегда, это и есть критерий деления |
| композиция вместо наследования | сборка из мелких вместо флагов в опциях | в опциях появился флаг, включающий блок логики |
| фасад | крупный композабл только соединяет мелкие | компонент иначе вызывает четыре части в жёстком порядке |
| внедрение зависимости | вход приходит аргументом `MaybeRefOrGetter` | вход может быть другим или его надо подставить в тесте |
| стратегия | изменяемое решение передаётся функцией | набор режимов открыт и пополнится |
| шаблонный метод | порядок шагов внутри, содержимое шагов снаружи | повторяется последовательность, а не выражение |
| декоратор | сквозная забота навешивается снаружи | забота нужна нескольким композаблам и не принадлежит ни одному |
| адаптер | чужой императивный API заворачивается в ref-ы | API императивный, заменяемый или недоступен на сервере |
| фабрика | состояние создаётся на каждый вызов | у каждого вызова должно быть своё состояние |
| состояние | объединение с тегом вместо булевых флагов | два и больше флага, несовместимых между собой |
| сегрегация интерфейса | наружу то, что использует вызывающий | возвращаемый объект пухнет внутренними деталями |
| наблюдатель | руками не берётся, это `ref` и `watch` | никогда: изобретать оповещение поверх реактивности не надо |

Приёмы не исключают друг друга. Крупный композабл обычно фасад, чьи части получают вход аргументом, а одна из частей ещё и стратегию функцией.

## Флаги в опциях означают, что пора делить

Каждый флаг это ветка, и все ветки делят одно тело. Через три флага восемь сочетаний, и ни одно из них не проверено.

```ts
// хорошо: включено то, что собрали, остального в коде нет
const { query, matched } = useTextFilter(products, (product) => product.title)
const { sortKey, sorted } = useSort(matched)
const { selected, toggle } = useSelection(matched)
```

```ts
// плохо: поведение выбирается флагами, тело у всех вариантов общее
const table = useTable(products, {
  sortable: true,
  filterable: true,
  paginated: false,
  selectable: true,
})
```

Признак, что делить пора: в опциях появился флаг, который включает целый блок логики, а не настраивает существующий. `debounce: 300` это настройка, `selectable: true` это отдельная ответственность.

## Вход приходит аргументом

Композабл, который сам достаёт данные из стора, работает только в одном месте приложения и проверяется только вместе с этим стором. Тот же композабл с аргументом вызывается откуда угодно и проверяется массивом.

```ts
// хорошо: данные приходят аргументом, стор подключает вызывающий
export function useVisibleItems(source: MaybeRefOrGetter<Item[]>) {
  const visible = computed(() => toValue(source).filter((item) => item.visible))

  return { visible }
}
```

```ts
// плохо: зависимость взята изнутри, вызвать с другими данными нельзя
export function useVisibleItems() {
  const cart = useCartStore()
  const visible = computed(() => cart.items.filter((item) => item.visible))

  return { visible }
}
```

Тип аргумента `MaybeRefOrGetter<T>`, чтение через `toValue`. Тогда вызывающий передаёт `ref`, геттер или готовое значение, и композабл не диктует ему форму.

Исключение: композабл, чья задача и есть доступ к конкретному источнику. `useCartTotals` вправе взять `useCartStore` внутри, потому что без него он бессмыслен. Аргументами передаётся то, что может быть другим.

## Изменяемое решение передавай функцией

Строка режима внутри превращается в ветку, и каждый новый режим правит тело композабла.

```ts
// хорошо: правило сравнения передано снаружи, тело композабла не меняется
const { sorted } = useSort(items, (left, right) => left.price - right.price)
```

```ts
// плохо: новый порядок сортировки означает правку useSort
const { sorted } = useSort(items, "byPrice")
```

Берётся, когда набор вариантов открыт: сортировки, форматтеры, правила валидации, ключ сравнения.

Не берётся, когда набор действительно закрыт и не пополнится. Тогда объединение литералов лучше функции: оно проверяется типом, читается в месте вызова и не даёт передать что попало. Сомневаешься, закрыт ли набор, значит не закрыт.

## Порядок шагов фиксируй внутри, содержимое отдавай наружу

Стратегия подменяет одно решение внутри готового поведения. Шаблонный метод фиксирует порядок нескольких шагов и отдаёт наружу их содержимое. Признак, что нужен второй, а не первая: копируется последовательность, а не выражение.

```ts
// хорошо: переходы состояния описаны один раз, снаружи приходит только действие
export function useAsyncAction<T>(action: () => Promise<T>) {
  const status = ref<"idle" | "pending" | "done" | "failed">("idle")
  const error = ref<Error | null>(null)

  async function run() {
    status.value = "pending"
    error.value = null

    try {
      const result = await action()
      status.value = "done"

      return result
    } catch (cause) {
      error.value = cause as Error
      status.value = "failed"
    }
  }

  return { status, error, run }
}
```

```ts
// плохо: тот же try с теми же переходами скопирован в каждый композабл
export function useProducts() {
  const products = ref<Product[]>([])
  const isLoading = ref(false)
  const error = ref<Error | null>(null)

  async function load() {
    isLoading.value = true
    try {
      products.value = await fetchProducts()
    } catch (cause) {
      error.value = cause as Error
    } finally {
      isLoading.value = false
    }
  }

  return { products, isLoading, error, load }
}
```

Плохой вариант ломается не сразу. Он ломается на четвёртой копии, когда в одной из них забыли сбросить `error` перед повтором, и ошибка от прошлой попытки осталась висеть на экране.

Не берётся, когда шаг ровно один: тогда это обычная функция, а не приём.

## Сквозную заботу навешивай снаружи

Повтор при ошибке, задержка, логирование и замер времени не принадлежат ни одному композаблу. Встроив их внутрь, ты получишь их у всех вызовов и ещё один флаг в опциях.

```ts
// хорошо: забота добавлена снаружи, useAsyncAction о ней не знает
export function withRetry<T>(action: () => Promise<T>, attempts = 3) {
  return async () => {
    for (let attempt = 1; ; attempt++) {
      try {
        return await action()
      } catch (cause) {
        if (attempt >= attempts) throw cause
      }
    }
  }
}

const { status, run } = useAsyncAction(withRetry(loadProducts))
```

```ts
// плохо: повтор встроен внутрь, и это тот самый флаг, включающий блок логики
export function useAsyncAction<T>(action: () => Promise<T>, retry = false) {}
```

Оборачивается функция, а не композабл: у функции один вход и один выход, а у композабла возвращаемый объект, который придётся пересобирать целиком.

Берётся, когда забота нужна нескольким разным местам. Нужна одному, впиши на месте: обёртка ради одного вызова добавляет файл и не убирает ничего.

## Чужой императивный API заворачивай в композабл

Браузерные API, SDK и обычные библиотеки говорят колбэками и методами, а не реактивными значениями. Композабл переводит их на язык остального кода, и тогда замена библиотеки это правка одного файла.

```ts
// хорошо: обращение к браузеру заперто внутри, наружу вышел ref
export function useOnline() {
  const online = ref(true)

  function sync() {
    online.value = navigator.onLine
  }

  onMounted(() => {
    sync()
    window.addEventListener("online", sync)
    window.addEventListener("offline", sync)
  })

  onScopeDispose(() => {
    window.removeEventListener("online", sync)
    window.removeEventListener("offline", sync)
  })

  return { online }
}
```

```ts
// плохо: обращение к браузеру размазано по компонентам, на сервере оно упадёт
const online = ref(navigator.onLine)

onMounted(() => window.addEventListener("offline", () => (online.value = false)))
```

Начальное значение здесь `true`, а не `navigator.onLine`, потому что на сервере `navigator` не существует. Первое чтение уезжает в `onMounted`, и это общее правило для любого адаптера над браузерным API.

Берётся в трёх случаях: API императивный, API недоступен на сервере, библиотеку можно заменить. Ни одного из них нет, обёртка только добавляет слой.

## Состояние создаётся на каждый вызов

Место объявления `ref` решает, будет состояние своим или общим. Объявленный на уровне модуля, он общий для всего процесса, и на сервере это означает общий для всех запросов.

```ts
// хорошо: состояние создаётся вызовом, экземпляры не мешают друг другу
export function useToggle(initial = false) {
  const on = ref(initial)

  function toggle() {
    on.value = !on.value
  }

  return { on, toggle }
}
```

```ts
// плохо: ref на уровне модуля, на сервере его делят все запросы
const on = ref(false)

export function useToggle() {
  function toggle() {
    on.value = !on.value
  }

  return { on, toggle }
}
```

Плохой вариант выглядит рабочим на клиенте и течёт только при серверном рендеринге, где один пользователь видит состояние другого. Разбор в [nuxt/SSR.md](../nuxt/SSR.md).

Состояние действительно одно на приложение, композабл с модульным `ref` всё равно не годится: это хранилище, и его место в `pinia`, где у состояния есть имя, инструменты и корректный жизненный цикл на сервере.

## Несовместимые флаги замени объединением с тегом

Булевы флаги описывают состояния, которые не могут быть одновременными, и не мешают их получить. Уже на двух флагах появляется сочетание, которого не бывает: идёт загрузка, и тут же лежит ошибка от прошлой попытки.

```ts
// хорошо: невозможных сочетаний не существует, ветка сужает тип
type Load<T> =
  | { tag: "pending" }
  | { tag: "empty" }
  | { tag: "done"; data: T }
  | { tag: "failed"; error: Error }

const state = ref<Load<Product[]>>({ tag: "pending" })
```

```ts
// плохо: pending и failed могут стать истинными одновременно, и однажды станут
const isLoading = ref(false)
const isError = ref(false)
const isEmpty = ref(false)
```

Второй выигрыш в разметке: у ветки `state.tag === "done"` поле `data` существует и типизировано, а рядом с флагами данные лежат отдельным `ref` и могут быть пустыми в любой ветке.

Берётся с двух флагов, которые нельзя включить вместе. Флаг один, объединение лишнее. Правила про сами объединения лежат в `typescript`.

## Оповещение не изобретай

Реактивность уже даёт наблюдателя. Колбэк `onChange` между частями возвращает ручное оповещение и делает порядок вызовов значимым.

```ts
// хорошо: соседняя часть подписывается на источник сама
const { sortKey, sorted } = useSort(matched)
const { page, visible } = usePagination(sorted)
```

```ts
// плохо: оповещение вручную, и теперь важно, кого вызвали первым
const { sortKey } = useSort(matched, { onChange: () => (page.value = 1) })
```

Колбэк остаётся правильным выбором для события, а не для состояния. Отправка формы, попадание в аналитику, показ уведомления должны случиться ровно один раз на действие, а `watch` по значению не сработает, если новое значение совпало с прежним.

Правило короткое: состояние отдавай источником, событие колбэком.

## Общее состояние живёт в одном месте

Разрезав композабл, легко получить два `ref` про одно и то же. Они разъезжаются на первой правке, и найти, какой из них главный, потом нечем.

```ts
// хорошо: страницу держит тот, кто ей распоряжается, остальные её принимают
export function usePagination<T>(source: MaybeRefOrGetter<T[]>, size = 20) {
  const page = ref(1)
  const visible = computed(() => toValue(source).slice((page.value - 1) * size, page.value * size))

  watch(() => toValue(source), () => (page.value = 1))

  return { page, visible }
}
```

```ts
// плохо: своя страница внутри фильтра, теперь их две
export function useTextFilter<T>(source: MaybeRefOrGetter<T[]>) {
  const page = ref(1)
  const query = ref("")

  return { query, page, matched }
}
```

Частям нужно одно и то же состояние, передавай его аргументом, а не создавай заново.

## Очистку держит тот, кто подписался

Слушатель, наблюдатель и таймер снимаются в том же композабле, где созданы. Иначе фасад обязан помнить про каждую часть, и первая забытая часть течёт молча.

```ts
// хорошо: подписался внутри, там же и снял
export function useElementSize(target: Ref<HTMLElement | null>) {
  const width = ref(0)
  const observer = new ResizeObserver(([entry]) => (width.value = entry.contentRect.width))

  watch(target, (element) => {
    observer.disconnect()
    if (element) observer.observe(element)
  }, { immediate: true })

  onScopeDispose(() => observer.disconnect())

  return { width }
}
```

```ts
// плохо: снятие отдано наружу, вызывающий обязан о нём помнить
const { width, stop } = useElementSize(box)
onUnmounted(stop)
```

`onScopeDispose` привязан к активной области эффектов, а не к компоненту, поэтому работает и в композабле, вызванном из другого композабла. Композабл вызывается вне компонента, оберни вызов в `effectScope`, иначе снимать очистку будет некому.

## Где остановиться

Дробление стоит прыжков между файлами. Композабл на пять строк, который вызывается из одного места и больше никогда, дороже той же пятёрки строк на месте.

Проверяй частью, а не файлом: часть выделяется, если её можно вызвать в одиночку и проверить в одиночку. Не проходит проверку, остаётся внутри.

| Признак | Что делать |
| --- | --- |
| часть работает только после другой части, в одном порядке | оставить внутри, это фрагмент |
| часть вызывается из двух и более мест | вынести |
| часть меняется по своей причине, не совпадающей с остальными | вынести |
| часть проверяется только вместе с остальными | оставить внутри |
| у части свой набор внешних эффектов: запрос, слушатель, таймер | вынести, вместе с очисткой |

Имя мелкого композабла говорит, чем он владеет, а не откуда его вызвали. `useSort` и `useTextFilter` переиспользуются, `useProductTableSortPart` нет.

Куда положить файлы после дробления, к компоненту или в общий пакет, скилл не решает: держи рядом с компонентом, пока потребитель один. Правило про синхронный вызов в setup действует на каждую часть отдельно: мелкий композабл внутри `computed` или после `await` не зарегистрирует хуки, как и крупный.
