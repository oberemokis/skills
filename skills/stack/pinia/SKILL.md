# Pinia

> Точка входа: [skills/core](../../core/SKILL.md). Если core ещё не прочитан, прочитать его до этого скилла.

Версия: Pinia 4.0.3, `@pinia/nuxt` 1.0.2. Требует Vue от 3.5.11 и TypeScript от 5.6, со стеком совпадает.

Версия выше не украшение. Правила про поведение переживают мажорные обновления, а всё из раздела «Привязано к версии» перестаёт быть верным вместе с ней: если в `package.json` версия другая, сверь имена до того, как напишешь.

Pinia не установлена ни в одном проекте. Скилл написан по документации, соглашений из кода здесь нет, и первый его раздел про то, как обойтись без неё.

## Когда применять

- состояние нужно многим несвязанным потребителям и переживает переходы между страницами
- производное состояние сложное, и его пересчёт хочется держать в одном месте
- нужны инструменты разработчика с историей изменений состояния

## Когда НЕ применять

- состояние живёт внутри компонента: обычный `ref`, это `vue`
- состояние нужно двум-трём соседним компонентам: композабл, а в Nuxt `useState`, это `nuxt`
- фильтры, сортировка, страница списка: источником истины должен быть адрес страницы, тогда состояние переживает перезагрузку и делится ссылкой
- кеш ответов сервера: это `useAsyncData` и `useFetch`, у них уже есть ключи и инвалидация

Разница между проектами существенная. В Nuxt почти всё закрывается `useState` и загрузкой данных, поэтому хранилище там нужно редко. В приложении на чистом Vue без Nuxt такой замены нет, и порог для Pinia ниже.

## Правила

### Setup-хранилище обязано вернуть всё состояние

Не возвращённый `ref` остаётся живым, но невидимым для гидратации, инструментов разработчика и горячей замены. Ломается это не сразу и не очевидно.

```ts
// хорошо
export const useCartStore = defineStore("cart", () => {
  const items = ref<Item[]>([])
  const total = computed(() => items.value.length)

  function add(item: Item) {
    items.value.push(item)
  }

  return { items, total, add }
})
```

```ts
// плохо: items не вернули, SSR и devtools его не увидят
export const useCartStore = defineStore("cart", () => {
  const items = ref<Item[]>([])
  const total = computed(() => items.value.length)

  return { total }
})
```

### Состояние и геттеры достаются через storeToRefs

Обычная деструктуризация снимает реактивность, и значение перестаёт обновляться.

```ts
// хорошо
const store = useCartStore()
const { items, total } = storeToRefs(store)
const { add } = store
```

```ts
// плохо: items и total больше не обновятся
const { items, total } = useCartStore()
```

Действия деструктурировать можно прямо из хранилища: они привязаны и реактивность им не нужна.

### Хранилище вызывается внутри setup, а не на уровне модуля

Вызов до установки плагина даёт ошибку «no active pinia».

```ts
// хорошо
export function useCartActions() {
  const store = useCartStore()
  return { add: store.add }
}
```

```ts
// плохо: выполнится при импорте, до app.use(pinia)
const store = useCartStore()
export function useCartActions() {
  return { add: store.add }
}
```

### Хранилища мелкие и по смыслу, а не одно на приложение

Одно большое хранилище означает, что любой компонент подписан на всё, а границы ответственности не видны. Дели по предметной области.

```ts
// хорошо
export const useCartStore = defineStore("cart", () => {})
export const useAuthStore = defineStore("auth", () => {})
```

```ts
// плохо: компонент корзины подписан и на профиль, и на настройки
export const useAppStore = defineStore("app", () => {
  const cartItems = ref<Item[]>([])
  const currentUser = ref<User | null>(null)
  const uiSettings = ref<Settings>(defaultSettings)
  return { cartItems, currentUser, uiSettings }
})
```

### Запросы к серверу живут снаружи действий

Действие меняет состояние, а не ходит по сети. Запрос выносится в отдельную функцию или композабл, действие принимает уже готовые данные.

```ts
// хорошо
async function load() {
  items.value = await fetchCart()
}
```

```ts
// плохо: хранилище знает про транспорт, подменить его в тесте нечем
async function load() {
  const res = await fetch("/api/cart", { headers: authHeaders() })
  items.value = await res.json()
}
```

Это же правило делает хранилище тестируемым без подмены своих модулей, как требует `test`.

## Привязано к версии

Четвёртый мажор ломающих изменений в API не принёс, поэтому правила выше верны и для третьей версии. Технические отличия такие.

| Было в 3 | Стало в 4 |
| --- | --- |
| сборка с CommonJS | только ESM |
| `@vue/devtools-api` шёл внутри | ставится рядом как зависимость |
| обычные сообщения об ошибках | диагностика с проверкой аргументов `storeToRefs` и значений в плагинах |

## Антипаттерны

| Не так | Так | Почему |
| --- | --- | --- |
| хранилище там, где хватает `useState` или композабла | начать с меньшего | хранилище добавляет слой, который потом никто не убирает |
| фильтры и пагинация в хранилище | адрес страницы как источник истины | иначе состояние теряется при перезагрузке и не передаётся ссылкой |
| деструктуризация хранилища напрямую | `storeToRefs` для состояния и геттеров | реактивность снимается молча |
| вызов `useStore()` на уровне модуля | внутри setup или функции | до установки плагина активного экземпляра нет |
| setup-хранилище, вернувшее часть состояния | вернуть всё | невозвращённое не гидратируется и не видно в devtools |
| одно хранилище на всё приложение | деление по предметной области | подписка на всё и размытые границы |
| `fetch` внутри действия | запрос снаружи, действие принимает данные | иначе транспорт нельзя подменить в тесте |
| хранилище как кеш ответов сервера | `useAsyncData` с ключом | у него уже есть ключи, дедупликация и инвалидация |
