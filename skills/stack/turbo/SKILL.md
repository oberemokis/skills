# Turbo

> Точка входа: [skills/core](../../core/SKILL.md). Если core ещё не прочитан, прочитать его до этого скилла.

Версия: turbo 2.5.8 в обоих монорепозиториях, в npm уже 2.10.11. Рабочие пространства на pnpm, раскладка `apps/api/*`, `apps/web/*`, `libs/*`, `packages/*`, `shared/*`.

Версия выше не украшение. Правила про поведение переживают мажорные обновления, а всё из раздела «Привязано к версии» перестаёт быть верным вместе с ней: если в `package.json` версия другая, сверь имена до того, как напишешь.

## Когда применять

- правишь `turbo.json`, добавляешь задачу или пакет
- кеш попал, когда не должен был, или промахнулся, когда должен был попасть
- задачи идут последовательно там, где могли бы параллельно

## Когда НЕ применять

- зависимости, каталоги версий, рабочие пространства: это `pnpm`
- конфигурация сборки внутри пакета: это `vite`
- конфигурация тестов: это `vitest`

## Что в текущем конфиге стоит починить

Разобрано по `turbo.json` и корневым скриптам обоих репозиториев. Правила ниже объясняют каждый пункт.

- `lint` объявлен корневым скриптом `oxlint`, а не задачей turbo: линт не кешируется, не параллелится и не фильтруется
- у задачи `typecheck` пустая конфигурация: нет `dependsOn`, поэтому правка исходников зависимости не инвалидирует тайпчек зависимого пакета
- в tsconfig включён `incremental`, значит `tsc` пишет `.tsbuildinfo`, а в `outputs` у `typecheck` не объявлено ничего
- `tsconfig.base.json` в корне не объявлен в `globalDependencies`: его правка не инвалидирует ни одну задачу
- ни `env`, ни `globalEnv` не объявлены нигде, при этом кодогенерация remotes для федерации модулей почти наверняка зависит от окружения
- `gen:remotes` вызывается через хуки `predev` и `prebuild` пакетного менеджера, то есть вне графа: его входы не хешируются, а результат не кешируется

## Правила

### Задачи живут в пакетах, а не в корне

Корневая задача выполняется один раз, целиком, без кеша на пакет и без возможности отфильтровать. Это самая частая ошибка в монорепе.

```json
// хорошо: turbo.json
{
  "tasks": {
    "lint": { "dependsOn": ["transit"] }
  }
}
```

```json
// плохо: корневой package.json
{
  "scripts": { "lint": "oxlint" }
}
```

Скрипт объявляется в каждом пакете, задача регистрируется в корневом `turbo.json`, а корневой `package.json` только делегирует: `"lint": "turbo run lint"`.

Корневая задача через `//#task` оправдана там, где её физически нельзя разложить по пакетам: сквозной прогон Vitest через `projects`, релизные скрипты, инструмент, который сам не зовёт turbo. Браузерные тесты через Playwright тоже сюда: им нужно поднятое приложение целиком.

### В коде всегда turbo run

```json
// хорошо
{ "scripts": { "build": "turbo run build" } }
```

```json
// плохо
{ "scripts": { "build": "turbo build" } }
```

Короткая форма существует для разовых команд, набранных руками. В скриптах, в CI и в документации пишется полная: она не сломается, когда появится задача с именем, совпадающим с флагом.

### Каретка в dependsOn означает зависимости, её отсутствие означает свой пакет

```json
// хорошо
{
  "tasks": {
    "build": { "dependsOn": ["^build"], "outputs": ["dist/**"] },
    "preview": { "dependsOn": ["build"] }
  }
}
```

```json
// плохо: задача ждёт саму себя
{
  "tasks": {
    "build": { "dependsOn": ["build"] }
  }
}
```

`^build` собирает сначала пакеты, перечисленные в зависимостях. Ключевое следствие: **не объявлена зависимость в `package.json`, значит порядка нет**. Каретка не угадывает связи, она читает граф пакетов.

Отсюда правильный разбор скриптов `prebuild`: если зависимость объявлена, хук не нужен, порядок обеспечит `^build`. Если не объявлена, сначала объявить, потом убрать хук.

### Задачам, читающим исходники зависимостей, нужен транзитный узел

Это про `typecheck` и `lint`. Они читают исходники зависимостей, но не нуждаются в результатах их сборки. Наивные варианты оба неверны: `dependsOn: ["^typecheck"]` делает прогон последовательным без нужды, а пустой `dependsOn` даёт неверный кеш, потому что правка зависимости не инвалидирует зависимого.

```json
// хорошо: транзитный узел связывает пакеты, не заставляя ждать
{
  "tasks": {
    "transit": { "dependsOn": ["^transit"] },
    "typecheck": { "dependsOn": ["transit"], "outputs": [".tsbuildinfo"] },
    "lint": { "dependsOn": ["transit"] }
  }
}
```

```json
// плохо: кеш попадёт, хотя исходники зависимости изменились
{
  "tasks": {
    "typecheck": {}
  }
}
```

Задачи `transit` в пакетах не существует, и это нормально: узел нужен только для связей в графе.

Признак задачи, которой нужен такой узел: она читает файлы зависимостей, но не их `dist`.

### Переменные окружения объявляются, иначе кеш врёт

Turbo не читает `.env` сам, но должен знать о его изменении. И любая переменная, влияющая на результат, обязана попасть в хеш.

```json
// хорошо
{
  "globalEnv": ["NODE_ENV"],
  "globalDependencies": ["tsconfig.base.json"],
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "env": ["API_URL", "REMOTE_ENTRY_URL"],
      "inputs": ["$TURBO_DEFAULT$", ".env", ".env.*"],
      "outputs": ["dist/**"]
    }
  }
}
```

```json
// плохо: сборка со staging-адресом вернётся из кеша для продакшена
{
  "tasks": {
    "build": { "dependsOn": ["^build"], "outputs": ["dist/**"] }
  }
}
```

Отдельная ловушка: `passThroughEnv` отдаёт переменную в рантайм, но **не** участвует в хеше. Она для того, что на результат не влияет: токены доступа, идентификаторы прогона CI. Положив туда `API_URL`, вы получите кеш, отдающий сборку с чужим адресом.

Вторая: переменная, вычисленная в процессе, невидима. `export API_URL=$VALUE && vite build` не попадёт в хеш никогда, надо `API_URL=$VALUE turbo run build`.

Большой массив `env` на пятьдесят строк это не проблема и не повод сокращать: он означает, что автор аккуратно перечислил зависимости сборки.

### Не затирай стандартные входы

```json
// хорошо
{ "inputs": ["$TURBO_DEFAULT$", ".env"] }
```

```json
// плохо: перестанет замечать правки исходников
{ "inputs": ["src/**"] }
```

`$TURBO_DEFAULT$` разворачивается в стандартный набор отслеживаемых файлов. Без него вы заменяете его целиком своим списком.

Файл за пределами пакета адресуется через `$TURBO_ROOT$`, а не относительным путём: `"$TURBO_ROOT$/tsconfig.base.json"`.

### Объявляй то, что задача действительно пишет

```json
// хорошо
{
  "tasks": {
    "build": { "outputs": ["dist/**"] },
    "typecheck": { "outputs": [".tsbuildinfo"] },
    "test": { "outputs": ["coverage/**", ".vitest/**"] }
  }
}
```

```json
// плохо: при incremental в tsconfig tsc пишет .tsbuildinfo, а turbo про него не знает
{
  "tasks": {
    "typecheck": {}
  }
}
```

Отсутствие `outputs` законно для задач, которые ничего не пишут, кроме вывода в терминал. Но проверь фактически: при `incremental` или `composite` в tsconfig `tsc --noEmit` всё равно создаёт `.tsbuildinfo`, и незаявленный файл ломает восстановление из кеша.

Задачи с побочными эффектами не кешируются вовсе, а долгоживущие обязаны быть отмечены:

```json
{
  "tasks": {
    "deploy": { "dependsOn": ["build"], "cache": false },
    "dev": { "cache": false, "persistent": true }
  }
}
```

Без `persistent` зависимые задачи будут ждать, пока dev-сервер «закончится».

### Фильтруй графом, а не руками

```bash
# хорошо
turbo run test --affected
turbo run build --filter='./apps/web/*'
```

```bash
# плохо: список разъедется с реальными зависимостями
turbo run build --filter=web --filter=shared --filter=ui
```

`--affected` сравнивает с основной ветвью и сам добавляет зависимых. Базу можно сменить: `--affected --affected-base=origin/develop`.

Флаг `--parallel` обходит граф зависимостей. Если задачи должны идти параллельно, это лечится правильным `dependsOn`, а не флагом.

### Кодогенерация это задача, а не хук пакетного менеджера

```json
// хорошо
{
  "tasks": {
    "gen:remotes": {
      "inputs": ["scripts/gen-remotes.ts", "$TURBO_ROOT$/pnpm-workspace.yaml"],
      "outputs": ["src/remotes.generated.ts"],
      "env": ["REMOTE_ENTRY_URL"]
    },
    "build": { "dependsOn": ["gen:remotes", "^build"] }
  }
}
```

```json
// плохо: хук вне графа, входы не хешируются, результат не кешируется
{ "scripts": { "prebuild": "pnpm gen:remotes" } }
```

## Привязано к версии

Ключи из правил выше стабильны в пределах второй мажорной версии. Проверять надо не их, а свежие возможности: между 2.5.8 и 2.10.11 пять минорных выпусков, и часть флагов оттуда в вашей версии просто не существует. Перед тем как закладывать незнакомый ключ, посмотри `turbo --version` и changelog.

## Антипаттерны

### Кеш попадает, когда не должен

```json
// плохо
{
  "tasks": {
    "build": { "outputs": ["dist/**"] }
  }
}
```

Переменные не объявлены, `.env` не в `inputs`, корневой конфиг не в `globalDependencies`. Сборка для другого окружения вернётся из кеша, и это самый дорогой вид ошибки: он не падает, а тихо разворачивает не то.

### Кеш промахивается, когда должен попадать

```json
// плохо
{
  "globalDependencies": ["**/*.ts"]
}
```

`globalDependencies` бьёт по глобальному хешу всех задач во всех пакетах, и отказаться от него отдельная задача не может. Широкая маска означает, что любая правка инвалидирует всё.

То же с корневым `tsconfig.json`, который правят часто: он должен быть объявлен, но узко и осознанно.

### Диагностика

```bash
# хорошо: посмотреть, из чего собран хеш, и сравнить два прогона
turbo run build --summarize
# затем diff .turbo/runs/<id>.json

turbo run build --dry=json     # что запустится и почему
turbo run build --force        # прогнать без чтения кеша
turbo run build --output-logs=new-only
```

Порядок разбора при неожиданном промахе: сравнить два `--summarize`, проверить переменные через `--dry=json`, посмотреть, не менялся ли лок-файл и `turbo.json`. При неожиданном попадании: искать переменную, которой нет в `env`, файл, которого нет в `inputs`, или файл за пределами каталога пакета.

### Прочее

| Не так | Так | Почему |
| --- | --- | --- |
| зависимость приложения в корневом `package.json` | в пакете, который её использует | корневая установка меняет лок-файл и инвалидирует все кеши |
| `turbo.json` в пакете без `"extends": ["//"]` | добавить `extends` | иначе конфиг невалиден |
| импорт через относительный путь за границу пакета | по имени пакета | относительный путь ломает границы и графы |
| `--env-mode=loose`, чтобы прошли переменные CI | `globalPassThroughEnv` со списком | ослабление режима снимает защиту целиком |
| общий код внутри приложения | отдельный пакет | иначе его нельзя переиспользовать и кешировать |
