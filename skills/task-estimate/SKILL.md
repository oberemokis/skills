# Task estimate

> Точка входа: [core](../core/SKILL.md). Если core ещё не прочитан, прочитать его до этого скилла.

## Маршрут

1. Прими аргументы work и открой [маршрут task-run](../task-run/SKILL.md). В той же сессии по его правилам выполни подключение проекта, start и worktree: задача с комментариями, критерии, факты в коде, потребители, тестовые швы и свежая `context.map`. На продолжении бери готовое из файла задачи. Соблюдай его учёт времени и остановки с самого начала.
2. Составь черновик плана по [этапу plan](../task-run/stages/plan.md): что поменяется, где и чем это проверить. Если выбор продукта или неизвестная причина бага меняют набор правок, покажи конкретный вопрос, отложи число до ответа или диагностики. Не подставляй резерв за неизвестность. Если ручная оценка появилась за время разведки, используй её как есть.
3. Перед вопросом о запуске зафиксируй прогноз по разделу ниже и запиши файл задачи по [state.md](../task-run/state.md). Передай управление `task-run` с текущего **вопроса плана**. Покажи план, минуты, источник, временной уровень и уровень проверки одним сообщением. Вторая сессия, повторная разведка и второе согласование не нужны. При рестарте используй сохранённый план; проверяй свежесть карты обычным способом.

## Расчёт

Цель: активные минуты **всей задачи**, от начала разведки до закрытия. Именно на этот интервал есть списания. Это не срок доставки: ожидание пользователя, продукта и пайплайна исключается правилами `task-run`. Уже потраченное на разведку входит в прогноз; не прибавляй его второй раз.

- `F`: число уникальных путей в `context.map.files`, которые план затрагивает. Тестовый файл тоже считается, если его предстоит править; файл только для чтения не считается. Повторные ссылки на один путь дают единицу.
- `C`: число отдельных проверяемых случаев в плане (`context.cases`); десяток команд, прогоняющих один случай, не даёт десять случаев. У чистой текстовой правки бывает ноль. Нет плана с конкретным местом правки: оценку не выдавай.
- Формула: `T = max(1, round(base + perExtraFile × (F − 1) + perCase × C))`. Начальные веса: **5, 1, 3** минуты. Это регрессия по историческим планам; коэффициент не означает, что любой тест занимает ровно три минуты.
- Уровень времени по итоговому `T`: **T1** ≤15 минут, **T2** 16–30, **T3** 31–60, **T4** 61–120, **T5** >120. Границы для очереди настраивает проект. Рядом показывай `S/M/L` из task-run: короткая правка контракта может быть `T1 / L`.

Вызови `node <папка скилла>/scripts/estimate.mjs plan F C`. Для готового числа: `node <папка скилла>/scripts/estimate.mjs manual N`; так определяется только T-уровень, исходные минуты остаются. Конфиг по умолчанию [model.json](model.json); если в папке состояния проекта есть `estimate-model.json`, передай `--config <абсолютный путь>` при **каждом** расчёте, включая ручной и симуляцию. Это полная копия `model.json`, можно менять каждый вес и четыре порога по отдельности. Некорректный конфиг исправь, не подменяй его умолчаниями.

Пример: «4 файла, 7 случаев: 5 + 3 + 21 = 29 минут, T2. Проверка L: меняется API». Вне исторического диапазона (в стартовой выборке 1–9 файлов и 0–16 случаев) или при сложной миграции явно назови экстраполяцию. Время по названию тикета, приоритету, S/M/L или оценке в человеко-днях не выводи.

## Настройка по истории

Метод, команды и результат первого прогона: [симуляция](simulation.md). Для повторного прогона используй папку `tasks` своего проекта: `node <папка скилла>/scripts/estimate.mjs simulate <путь-к-tasks> N`, где `N` старых завершённых задач идут на подбор, остальные на проверку. Сравни MAE (среднюю абсолютную ошибку), bias (плюс означает завышение) и худшую ошибку. Смотри `n`: у трекера могут быть пары только для части задач. Команда печатает веса-кандидаты и не меняет конфиг. Если новый профиль устойчиво лучше на последующих задачах, перенеси `fitted` в проектный `estimate-model.json`.
