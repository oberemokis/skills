# Audit

> Точка входа: [skills/core](../core/SKILL.md). Дефект с известным симптомом чинится через [skills/test/bug-hunting](../test/bug-hunting/SKILL.md), а не здесь.

Аудит выдаёт список, а не правку. Результат один: полотно находок, ранжированное по последствию, где каждая строка называет файл, строку и сценарий отказа.

Порядок жёсткий, каждый шаг после предыдущего.

1. договориться о режиме, осях и уровне усилия
2. закрепить границы прогона
3. отдать инструментам считаемое
4. пройти оси моделью
5. отфильтровать по уверенности
6. выложить полотно в чат
7. предложить сохранение
8. чинить сверху вниз

## Сначала спроси, потом смотри

Режим и оси выбирает пользователь. Не начинай с чтения кода: аудит без границ превращается в пересказ репозитория, а пересказ невозможно ни проверить, ни закрыть.

Спроси одним раундом, двумя вопросами, в формате [grill](../grill/SKILL.md): смайлик на вопросе, варианты буквами, рекомендация отдельным абзацем. Оси выбираются несколькими, поэтому букв там больше четырёх: это исключение из правила грилла.

```
❓ Q1. Что смотрим?
   - A) текущий незакоммиченный дифф
   - B) дифф от названной точки отсчёта
   - C) один пакет или каталог целиком
   - D) вся монорепа по пакетам

   Рекомендую: A, на нём быстрее всего получить полотно.

❓ Q2. Какие оси проверяем? Можно несколько.
   - A) корректность
   - B) молчаливые падения
   - C) инварианты и типы
   - D) мёртвый код
   - E) устаревшие API
   - F) расхождения
   - G) тесты

   Рекомендую: A, B и F, это то, что ломает поведение или обманывает читателя.
```

Пользователь ответил не на всё, назови взятое по умолчанию и продолжай: дифф, а из осей A, B и F. Молча подставленный режим потом объясняет находки, которых не ждали.

Уровень усилия задаётся аргументом при вызове, например `/oberemokis-skills:audit high`. Без аргумента берётся medium, и это пишется в шапке прогона. Вопросом в раунде его не спрашивай: пять вариантов не влезают в правило двух-четырёх. Пользователь выбирает уровень аргументом, зная, что он меняет:

| Уровень | Что меняется |
| --- | --- |
| low | инструменты и выбранные оси в границах прогона, без проверки находок по вызывающим местам |
| medium | как low, и находки корректности и молчаливых падений проверяются по вызывающим местам через grep |
| high | проверка по вызывающим местам для всех находок, и второй проход по корректности |
| xhigh | как high, и второй проход по всем выбранным осям |
| max | как xhigh, и второй проход охватывает весь пакет, а не только файлы из диффа |

Уровень меняет глубину прохода, но не порог записи. Находка без проверенного адреса, входа и отказа не попадает в полотно ни на каком уровне, см. раздел «Что выбрасывать».

## Границы

Аудит только читает код. Правки в файлах в этом прогоне не делаются, в том числе автоисправление линтера и форматирование: файлы остаются такими, какими были до вызова, иначе полотно описывает уже другой код. Если инструмент умеет чинить сам, запускай его в режиме проверки.

Закрепи точку отсчёта командой и покажи её вывод. Хорошо, когда ветка для сравнения проверена на существование и сразу видна статистика диффа от её развилки. Плохо, когда дифф берётся без названной точки и объём выяснится в середине прогона. Пустой дифф или неразрешённый ref это остановка, а не пустой отчёт.

Больше восьмисот строк диффа или больше одного пакета за проход не бери. Находки начинают вытеснять друг друга: последние файлы получают внимание по остаточному принципу, и это незаметно в отчёте. Режь по пакетам, полотно делай накопительным.

## Инструменты идут первыми

Считаемое считают инструменты, модель разбирает остаток. Прогони и возьми вывод как вход, до чтения кода.

Хорошо запустить типчекер, линтер в режиме тишины, поиск неиспользуемого кода с выводом в машиночитаемом виде и проверку устаревших зависимостей по всем пакетам: каждый из них даёт находки, которые не спорят. Плохо искать то же самое поиском по тексту, это дороже и даёт ложные срабатывания.

Команды берутся из скриптов проекта, а не из памяти. Точки входа фреймворка (страницы, роуты, плагины, автоимпорты) выглядят мёртвыми в выводе поиска неиспользуемого кода, и такой экспорт перед занесением в полотно проверяй по ссылкам отдельно.

Находки инструментов кладутся в полотно наравне с остальными, с пометкой источника. Своими словами их не переписывай: формулировка типчекера точнее и проверяется одной командой.

## Оси

За осью закреплён вопрос, а не тема. Вопрос заставляет искать конкретный вход, тема заставляет рассуждать.

- корректность: при каком входе результат станет неверным
- молчаливые падения: где ошибка проглатывается, где фолбэк прячет отказ, где catch шире причины
- инварианты: какое недопустимое состояние тип разрешает выразить
- мёртвый код: кто вызывает этот экспорт, ответ берётся у инструмента
- устаревшие API: что снято в мажоре, который стоит в `package.json`
- расхождения: документация против кода, тип против рантайм-валидации, имя против поведения, одно правило в двух местах
- тесты: ось ведёт в [skills/test/test-review](../test/test-review/SKILL.md), здесь не дублируется

## Формат находки

Одна находка это четыре строки: адрес, дефект, отказ, действие. Без любой из них находку нельзя ни проверить, ни закрыть. Адрес стоит первой строкой с квадратом уровня, три остальные идут под ним списком с отступом. Квадрат же отделяет находку от соседней, пустая строка между находками нужна только для того, чтобы разметка не склеилась.

```markdown
🟥 P1 · A-03 · packages/checkout/src/total.ts:42 · корректность
   - Дефект: скидка применяется до налога, итог занижен на налог со скидки.
   - Отказ: корзина 1000, скидка 10%, ставка 20% дают 1080 вместо 1092.
   - Чинить: перенести вызов applyDiscount ниже computeTax.
```

```markdown
🟩 P3 · A-07 · packages/checkout/src/legacy.ts · мёртвый код
   - Дефект: экспорт formatLegacy нигде не импортируется, инструмент поиска мёртвого кода отметил его как неиспользуемый.
   - Отказ: нет, поведения не меняет, растёт поверхность при каждом рефакторинге.
   - Чинить: удалить экспорт вместе с файлом, если он пуст без него.
```

Ниже пример, который нельзя выводить. Это то, что пишется по инерции при неуверенности. Ни адреса, ни входа, ни действия: закрыть такую строку нечем, и она проживёт в полотне до конца его дней.

```markdown
# плохо: квадрата нет, адреса нет, отказа нет
Возможно, стоит пересмотреть расчёт в total.ts, логика выглядит запутанной.
```

Идентификатор стабильный: префикс прогона и номер. По нему находку закрывают, на неё ссылаются в сообщении коммита и её узнают на следующем прогоне.

## Уровни

Уровень задаёт последствие, а не сложность починки. Однострочная правка бывает P1, переписывание модуля бывает P3.

- 🟥 P1, сломанное поведение: неверный результат, потеря данных, падение на реальном входе
- 🟨 P2, отложенный ущерб: молчаливое падение, инвариант, допускающий недопустимое, расхождение, которое обманет следующего читателя
- 🟩 P3, стоимость сопровождения: мёртвый код, дубль, устаревший API без снятия на горизонте

Уровень ставится каждой находке, включая пришедшие от инструментов. Полотно без уровней читают сверху вниз и бросают на трети. Квадрат ставится в чат и в файл, цвет читается раньше текста: красное сверху, зелёное внизу.

## Что выбрасывать

Пиши только то, что проверил. Полотно из десяти проверенных строк разбирают, полотно из сотни сомнительных закрывают и больше не открывают.

Не заносится:

- то, что уже поймали типчекер, линтер или тесты, их вывод и так в полотне
- предсуществующее вне границ прогона, кроме P1
- стилевые придирки, не записанные в `CLAUDE.md` проекта
- решения, объяснённые комментарием рядом или записью в ADR
- «можно бы обобщить» без названного второго места использования

## Полотно в чат

Сначала чат, файл потом. Сортировка по уровню, внутри уровня по файлу.

Первой строкой шапка прогона: границы, уровень усилия, какие инструменты запускались, счёт по уровням с квадратами, например `🟥 2 · 🟨 5 · 🟩 9`. Она отвечает на первый вопрос читающего, всё ли посмотрели, и на второй, с чего начинать.

Каждый уровень открывается своим заголовком: `### 🟥 P1, сломанное поведение`, и под ним его находки. Пустой уровень не пропускается, в нём пишется «нет»: читающий должен видеть, что уровень проверен, а не забыт.

## Файл предлагай, а не создавай

Спроси, сохранять ли полотно и куда: `docs/review/<дата>-<область>.md` в репозитории, файл во временной папке сессии, не сохранять.

Без ответа в репозиторий не пиши. Аудит запускают и на чужом коде, где лишний файл придётся объяснять в PR.

Сохранил, добавь каждой находке статус: открыто, чиню, закрыто, не баг. Следующий прогон читает этот файл первым и сверяется по идентификаторам, иначе он приносит те же находки заново и воскрешает то, что уже разобрали.

## Починка

Чини сверху вниз, по одной находке, и отмечай статус сразу. P1 с воспроизведением уходит в [skills/test/bug-hunting](../test/bug-hunting/SKILL.md): цикл, минимизация, регрессионный тест на правильном шве. P2 и P3 чинятся правкой и закрываются в полотне.

Не чини всё за один проход. Дифф на двадцать находок не ревьюится, а правка P3 внутри него прячет регресс от P1.

## Антипаттерны

### Аудит вместо работы

```
# плохо: прогон по всей монорепе «чтобы посмотреть»
120 находок, ни одна не закрыта, через неделю список устарел целиком
```

Аудит окупается объёмом, который разберут. Не знаешь, сколько разберут, бери один пакет.

### Находка без адреса

```markdown
# плохо: нечего открыть и нечем проверить
В обработке платежей встречается небезопасная работа с ошибками.
```

### Прочее

| Антипаттерн | Чем плох |
| --- | --- |
| удаление экспорта по одному слову инструмента поиска мёртвого кода | точки входа фреймворка в его выводе выглядят мёртвыми |
| пересказ вывода линтера своими словами | теряется точная формулировка, по которой правку проверяют |
| сохранение файла без спроса | в чужом репозитории его придётся объяснять в PR |
| смешение осей в одной находке | закрывается частями, статус становится неопределимым |
| находки сплошным списком без квадрата и отступа | уровень следующей находки не видно, пока не дочитаешь предыдущую |
